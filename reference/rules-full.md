# Clover 规则层 · 细则与判据

> `SKILL.md` = 精简入口（祈使句 + 路由）；本文件 = 同一套规则的细则 / 代价 / 出处 / 最小案例。
> **冲突时以 `SKILL.md` 为准**，并把差异报给用户；⛔ 两份都不许单方面改。
> **两份副本必须同步**（仓库源 `clover-ai-skill/` 与宿主安装副本）—— 独立目录，不是软链，只改一处 = 另一处仍是旧版。
> **指针指向空目标**（"详见 §X" / "见 `某文件.md` §Y" 而目标不存在）⇒ **报缺规则，⛔ 不许自己补**。
> **涉及工具 / 引擎 / 平台的行为，必须去源码或可复跑的实测输出里查**，⛔ 不许从"文档里的一句话"再推断一层。出处 = `文件:行` 或可复现的命令与输出。
> **教训必须匿名**：可写"做过什么错 / 代价多大 / 正确形状是什么"；⛔ 不许写项目名 / 专属路径 / 专属类名 / 只有那个项目能对上的数字。判据：读到的人能把它套到自己项目上。

## §0 ★★★ 第零铁律：做游戏 = 1:1 复刻 A

**"做一个游戏 <A>"下发时，目标已给定且唯一：把 A 一模一样搬过来。不许思考、不许权衡、不许改进。**
**唯一判据：A 有 ⇒ 做；A 没有 ⇒ 不加。** 用户没给参考游戏名 → **先停下问用户要**。

| ❌ 禁止的"思考" | ✅ 唯一正确动作 |
|---|---|
| 纠结"要不要做 / 值不值 / 能不能砍" | A 有 ⇒ 做 |
| 换更好看的颜色 / 字体 / 布局 / 素材 | 照抄 A 的（丑的、旧的、不合理的也照抄） |
| 手感优化 / 数值平衡 / UI 现代化 / 简化系统 | 照抄 A：A 的手感与数值就是标准 |
| 先写"我的方案 / 取舍建议"给用户看 | 不许产出方案，只许一张表：A 有什么 ⇒ 现在做到哪 |
| 自称"致敬 / 灵感源自 / 精简版 / 现代化重制" | 只准说：正在 1:1 复刻 A |
| 觉得做不到就自己换做法 | 先搜别人怎么复刻 A，照它的做法抄 |

**硬规则**：① 照抄 = 正确动作，不是偷懒；② 不许用"思考过程"替代劳动（回复与文档里不许出现"权衡之下 / 我建议先 / 考虑到…我选择"）；③ 不许问"要不要做" —— 参考游戏有的就自己做；④ A 的任何细节都不许自行判定"不重要"；⑤ 不许中途降标准（"差不多像" = 不像 = 不可交付）；⑥ 唯一例外：用户**本轮明说**"不必一模一样" —— 即便如此也要在交付说明首行写明降级原因。

### 用户只报了品类怎么办

**品类不是参考物，只有"某一款具体游戏"才是。**

| 情况 | 动作 |
|---|---|
| 用户报了具体游戏 | 直接用，1:1 复刻 |
| 只报品类 / 玩法 | **停下问一句**：给 2~3 个同品类但不同子类型的标杆候选，让用户挑；拿到名字立刻开工 |
| 用户回"你定 / 随便" | 由 AI 选定一个标杆，名字与理由写进 `策划/策划案/{A}参考规格.md` 顶部「形态」，照 §0 全程复刻它 |
| 用户报的是**形态**（MMO / 联机 / 单机） | 形态只决定"要不要服务端"（§4 闸门 0），不能替代参考物 |

**硬规则**：⛔ 禁止"没参考就自己从 0 设计"；**只问一次、只问一句**；候选不许拿"我们自己设计的方案"凑数；不替用户拍板（除非用户说"你定"）。

**"你定"时自选标杆的四条依据**：① 同品类（不跨品类）；② 载体可得（能拿到一手载体：rip / 反汇编 / 关卡数据 / 图集 / 官方 SDK；优先选有社区解包的老游戏）；③ 规模可交付；④ **只告知、不等待**（写进规格顶部 + 一句话告知，立刻开工）。

### 用户明说不做复刻怎么办

> 此时第零铁律被用户本人覆盖（用户 > 规则层），但标准答案换成**《用户规格书》**；⛔ 不许借"做原创"自由发挥，**验收强度一点都不降**。

| 事项 | 怎么做 |
|---|---|
| 唯一标准答案 | 把用户口述 / 文字 / 草图落盘成 `策划/策划案/原创规格.md`，**逐条编号**，开工前念回给用户确认一次 |
| 验收判据 | 每条规格必须带一个可执行判据（脚本断言 / 数值 / 视觉），没判据的条款不许进表 |
| §0.5 的"出处" | 从"参考物 `文件:偏移`"改成"**规格条款编号**"；指不出条款的常量一样不许进工程 |
| §0.7③ 基线图 | 换成「规格图」：用户草图 / 参考图 / 口述量化成的表 |
| §0.7④ diff 闭环器 | 保留，只把比对对象换成规格图 |
| §1.12 第 4 条 | 仍然成立：基准 = 规格书，⛔ 不是我们自己的实现说明 |
| 交付说明首行 | 写明「用户明说不做 1:1 复刻 ⇒ 按《原创规格》交付」 |

## §0.1 ⛔ 两件绝不打折的事

**病根：`实机次数 / 预算 / 轮次 / 上下文` 这类限额被读成"停工的许可证"。⇒ 这类限额一律废除 —— 它们是"怎么做得更省"，不是"可以不做"。**

### ① 必须做完 —— 没有任何限额能当停下来的理由

- ⛔ 不许**东拼西凑**（通用模板 / 别处片段 / 自创设施拼出"看起来能跑"的壳）；
- ⛔ 不许**糊弄**（占位色块 / 内置几何体 / 默认字体 / OnGUI 调试文字 / "留钩子后续替换" / "框架已预留" 全不算完成）；
- ⛔ 不许**缩水**（"先做精简版 / 这轮先到这儿 / 下一棒接着做 / 先汇报进度" = 没做完）；
- ⛔ **游戏是复合产物**：单维度做完 ≠ 做完（几何对 + 碰撞错 = 箱子能穿；动画数据在 + 没播 = 木头人；音频在 + 没挂事件 = 全程无声）→ 穷举口径见 `patterns/full-coverage-audit.md`；
- ⛔ 不许拿限额当借口：**验不完 ⇒ 继续验**（验到验收表零空行、零不一致）；**做不完 ⇒ 接力继续做**；
- **合法结束只有两种**：① 全部做完；② 真的被阻塞（缺的只有用户能给：本机文件 / 账号 / 付费 / 用户亲手点按钮 / 二选一决策），并说清"要用户给什么 + 拿到后我立刻做什么"；
- **唯一例外：规模判断失误 ⇒ 提一次「重新定范围」**（已完成 / 剩余量 / 2~3 个可选范围 + 各自代价 + 建议）。⛔ 与"不许问要不要继续"不冲突：问"要不要继续" = 违规，提"目标需要改范围" = 合法；⛔ 不附数字 ⇒ 照旧违规。

### ② 画面 / UI 必须和原版一个样 —— "数字对"永远不等于"做完了"

- **横版 / 竖版是这一条的第 0 项**：判错则整屏布局全错（先按 §4 闸门 0 判一次、写进规格顶部）。⛔ 不许没查就默认横屏。
- 用户点名 A ⇒ 默认 1:1（不是"像"）：横竖 / 布局 / 素材 / 字体 / 配色 / 尺寸 / 层级 / 间距 / 交互反馈 / 节奏逐项对齐 A 的原版画面。
- ⛔ **占位物 / 纯色块 / 默认 UI / 自画近似图 / 自己"设计"的布局** 一律不可交付。原版素材在手上却用纯色块拼 UI = 最典型的东拼西凑：先按 `reference/asset-sources.md` 出素材索引（帧号 ↔ 尺寸 ↔ 对应控件），再接面板。
- ⛔ **只报"数字全对 / 日志全绿"不算验收**：血条恒满、角色纯白无贴图、动画没播这类静默失效只有看图才发现（`表现类` 必须进联络图逐格读结论）。
- **判据**：交付前与 A 原版画面**同机位并排**逐项比，每项只允许写 `一致` / `不一致（差在哪）`；出现任何 `不一致` ⇒ 该版本不可交付，改完重截再比，循环到全一致。
- ⛔ 不允许"基本一致 / 大致像 / 略有差异 / 后续可优化" —— 那只是"没做完"的另一种说法。

## §0.5 ★★★ 复刻 = 解析 + 搬运（禁写条款）

> 一句话判据：**这个东西参考物里已经有了吗？有 ⇒ 必须解析出来，不许写。**

**1. 参考物里已有的东西禁止重新实现**。范围：几何与碰撞、模型顶点与骨骼、动画序列与帧率、贴图与字体、界面元素坐标/尺寸/颜色、数值与公式（速度 / 摩擦 / 重力 / 后坐力 / 散布 / 伤害 / 冷却 / 时长）、音频、文本排版。
- **正确**：从权威载体解析出来原样搬运；**禁止**凭理解 / 印象 / 常识在业务里重做一遍（"搭一个看起来像的""定一个合理的值"）。
- **判据**：**写不出出处的量一律不许进工程**；"看起来合理"不是出处。

**2. 开工第一步：定位并解析权威载体**

| 参考物形态 | 权威载体 | 动作 |
|---|---|---|
| 安装包 / 卡带 / 资源包 | ROM、MPQ / CASC、pak、assets | 解包 → 解析 → 落盘成可读数据 |
| 可执行程序 | 写死在代码里的常量与公式 | 读源码 / 反汇编 / 取常量表 |
| 地图 / 关卡文件 | 专用格式（BSP、TMX、自研表…） | 解析**原始结构**（笔刷 / 平面 / 网格），⛔ 不许栅格化成近似 |
| 只有参考图 | 图片本身 | 量化成表（x/y/w/h/RGB/层级）+ 同分辨率逐像素比对 |

**载体由执行者自己去弄到手**，不是等用户给。必须穷尽：**≥4 轮不同关键词（中英各半）× ≥3 类站点 × 换过格式与打包方式**（判据同 §4 闸门 3）；**"下不动"不算"没有"**。

**载体降级链**（每降一级都要登记"上一级为什么拿不到"）：① 可解包的原始数据（ROM / 资源包 / 安装文件）→ ② 可执行程序里的常量与公式（源码 / 反汇编）→ ③ 专用格式的原始结构（地图笔刷与平面、关卡字节表）→ ④ 参考图 / 视频（量化成表 + 逐像素比对）→ ⑤ 全拿不到 ⇒ 才升级为阻塞项，报清"缺什么 / 谁能给"。
⛔ 禁止"一边没载体、一边凭印象写"；⛔ 禁止把"我没去找"说成"没有载体"。

**3. 只有参考图时的边界**：图**能**锚静态视觉（布局 / 文字位置 / 色调 / 构图 / 模型比例）；图**锚不住**手感 / 动画节奏 / 交互反馈 / 音效时机（都是时间序列）⇒ 标 `BLOCKED：<缺什么 / 谁能给基线>` 或由人给基线，⛔ 不许凭印象定。图未覆盖关键状态（菜单 / HUD / 战斗 / 结算）⇒ 报缺，不许补。

**4. 唯一允许"自己设计"的情形**：参考物里确实不存在的东西 ⇒ 显式标注 **"本项目新增"**，并用**另一套**可验证标准验收（不与参考物比对）。

## §0.6 ★★★ 必然性规则不许只写在 skill 里

> **"提示词是请求，闸门才是保证。"** 完整论述见 `reference/deterministic-gates.md`。

**判定（按行为种类分）**：必须始终成立的硬性不变量 ⇒ 脚本 / 钩子 / 权限规则；偏好 · 概率性判断（风格 / 约定 / 倾向 / 措辞）⇒ 写在本 skill 里即可。
⚠️ **"零失败率"说的是执行，不是覆盖**：闸门还有三种失败模式 —— **假绿**（判据取错对象）/ **假红**（判据取错范围）/ **迎合**（判据判结果不判过程，改一个数字就能变绿）⇒ 它把"模型的概率性失败"换成"人的确定性错误"，划算但不是零。

**硬规则**：
0. ⛔ **闸门只有 5 条**（`SKILL.md` §6 第 2 条 · `reference/verify-template.md`）：① 编译 / 构建通过 ② 证据新鲜度 ③ 引用可达 ④ 交付卫生 ⑤ 脚本自己别崩。**其余一律是可选自检**，红了只当提示，⛔ 不许拿它拦交付。想加第 6 条 ⇒ 先过 `SKILL.md` §4 第 0 条那两句反问；过不了就别加。⛔ **不设 `planned` 列** —— 一标"计划中"就会有人把它当需求去实现，最后又长回几十项。
1. 本 skill 只装偏好类；凡是"必须始终成立"的，都必须同时存在于脚本或钩子里 —— **只写在这里 = 非零失败率 = 迟早被绕过**。
2. **三个落点**：① `tools/verify.ps1`（模板 `reference/verify-template.md`，**只有那 5 条**）；② **停止前钩子**（交付前跑脚本，有 FAIL 就拒绝结束）；③ **会话开始 / 每次提交注入必读卡**（只注入卡片，别灌正文）。
3. **为可闸门性设计工具面**：高风险动作做成专用、类型化入口，⛔ 不要藏在自由命令里。
4. ⛔ **外观验收的检测层绝不许用 AI"看图"**：用确定性**像素 diff**（pixelmatch / ODiff，基线须与运行时同环境生成）；**AI 只做分诊，终审是人**。
5. ⛔ **判据要判「过程」不判「结果」**：能靠改一个数字变绿的检查项还没在判该判的东西；判据必须指向**被测程序自己产生的记录**。
6. ⛔ **产物才算证据，叙述不算**：**L3** 被测程序自己写的标记 / **L2** 脚本采集产物 / **L1** 执行者写的文字（"已修复 / 已实测 / 确认一致"⛔ 不能当判据）/ **L0** 无产物 = 未验证。
   ⛔ **"每条判定行必须带机器锚点 + 五列表格 + 哈希"已删、不检了** —— 那是仪式（`SKILL.md` §4 第 0 条）：留下的只有上面这一句，**证据必须来自产物**。
7. **闸门自身也要被闸（这条不是仪式）**：① 闸门**必须能崩才算可靠** —— 崩了就判红、本次结论作废（第 5 条闸门）；② `reference/verify-template.md` 的 `GATE-ITEMS` 块是**参考清单**（`required` 计数 = 0）：**判据怎么实现、叫什么名字由项目自己定** ⇒ ⛔ **不对齐、不报缺名、也不报多余**；③ **本 skill 不提供自动对账脚本** —— 要就自己内联进项目 `tools/verify.ps1`，或者干脆不建（对账本身也是本轮精简掉的仪式）；④ 新增检查项**不要求**"两条自检"仪式，先问它值不值得存在（反问两句）。
- 三条的全文（三种失败模式 · 证据锚点 · L0~L3）→ `reference/anti-gaming.md`

## §1 ★★★ 第一铁律：必须做完，才交付

> **没做完 = 不许交付。没有"先给你看看"，没有"剩下一点下次补"。**

| 违规行为（出现即交付失败） | 正确做法 |
|---|---|
| **做一点交一点** | 闷头做完；中途只允许两种发言：被阻塞 / 全部做完 |
| 交付最小可运行版本 / 骨架 / 半成品 | 交付原版级完整成品 |
| 交付后补一句"其余还在路上" | 没做完就只说"还没做完" |
| **同一条回复里既说"完成"又列"还没验的 XXX"** | 与"做一点交一点"同罪 |
| 问"要不要继续 / 接下来做 X 吗 / 还需要我做什么 / 你看这样行吗" | ★ 这【不是】被阻塞，是变相进度播报 + 索取许可 ⇒ 删掉，继续做 |
| 用"范围太大 / 时间不够 / token 不够"砍范围 | 一律不许砍；物理上限用**接力**跨过去，不是用砍绕过去 |
| 东拼西凑（通用模板 / 别处片段拼壳） | A 有的按 A 做、A 没有的不加 |
| 拿"实机次数 / 预算 / 轮次 / 上下文"当停工理由 | 限额管的是"怎么做得更省"，不是"可以不做" |
| 数字全对就说"完成"，画面与 A 不像 | 不算做完：交付前同机位并排比到零不一致 |
| 在 A 之外自行发挥 / 先写方案给用户看 | 犯了第零铁律 |

**四条细则**：① 不许做一点交付一点；② 不许做最小可运行版本；③ 必须 1:1 复刻 A；④ "数字全对但画面不像" = 没做完。

## §1.5 ★★★ 收尾闸门：把话交回用户的唯一合法条件

> 被滥用过的两条停工漏洞：❌「我先汇报进度，下一棒继续做」；❌「验收表里有 N 行不一致，已登记，本轮到此」—— **登记 ≠ 交付**。

1. **合法结束只有两种**：① 全部做完（验收表零空行、零不一致、像不像 A 自审全一致）；② 真的被物理阻塞（缺的只有用户能给），且当轮说清「要用户给什么 + 拿到后我立刻做什么」。
2. ⛔ 禁止拿这些当停下理由：「上下文 / 预算快满」「实机次数用完了」「下一棒接着做」「已登记不一致 / 欠图」「先汇报让你知道进度」「我会继续做」。**实机次数 / 预算一律不设上限。**
3. **上下文 / 预算快满 ≠ 收尾**：正确做法是立刻把剩余工作拆成任务书、派新 agent 继续干；主 agent 只在真的没有可派之事时才结束这一轮。
4. **剩余项多于一个 agent 的量 ⇒ 分片派**（每片 2~3 项），一片一成员（team 异步，带成员名 + 队名）；可以多片并行；⛔ 不许走同步子 agent（会 `code=10003` 卡死）。⛔ 不许因为"一个 agent 做不完"就整体停下。
5. **验收表出现"不一致" ⇒ 该轮不许结束**：要么修到通过，要么转成显式阻塞项。素材 / 截图缺失同理：先去拿、先去拍。
6. **改 skill / 写文档 / 汇报**都属"停下来做的事"，只有第 1 条两种情形才允许；平时必须夹在连续干活的中间。
7. ⛔ **"离线自检通过"不能替代实机证据，但"实机证据"不等于"必须截图"**：按 §2 的类别走 —— `数值类` = 运行时日志行（离线断言只能作补充）；`表现类` = 必须进联络图。⛔ 反过来也不许给每个数值类行截图。
8. ⛔ **禁止用"交接文档"收尾**：不许产出 `docs/交接-*.md` / `NEXT.md` / `docs/进度*.md` 这类以"剩下没做的 / 下一棒从这里开始"为内容的文件。**接力 = 主 agent 立刻派新 agent**，不是留一份 md 给未来。例外：项目已交付后 `docs/` 作为历史记录冻结。

## §1.6 ★★ 品牌与署名（硬约束）

- **引擎名只有一个：`clover-engine`**。⛔ 禁止编造别名 / 花名 / 中译名 —— 界面、文档、注释、交付说明里出现非 `clover-engine` 的引擎自称，一律算 bug，立刻铲掉。
- **每个游戏的首页下方必须有一行署名 `by clover-engine`**（居底居中、字号小、颜色低调、不抢画面），写进 `策划/验收表.md` 一行并实机截图验证。
  - **"首页"= 玩家看到的标题屏 / 主菜单**，⛔ 不是"启动瞬间闪一下的那个画面"（启动画面有也不反对，但首页那处是硬要求）。
  - **判据是"渲染出来的东西"**：⛔ 只写在代码里不算、grep 到源码字符串不算 —— 必须在实机截图上看得见，且**逐字**（`by` / 连字符 / 大小写全对）。
  - 两种典型"源码全绿、画面不对"：① 署名只挂在启动画面、标题屏没有；② 用的是只有大写的像素字体 ⇒ 画面上渲染成 `BY CLOVER-ENGINE`（大小写不符同样不合规）。
  - ⇒ 判据必须是**运行时 UI 节点树里那个标签的实际文本 + 实际字体**（或字形比对），⛔ 不许 grep 源码字符串。（`engine-credit` 闸门条目**已删、不检了**：它本身判得对，但"署名有没有"人看一眼截图就知道，不值得占一条机械判据。）
- **顺手清理**：把自造出的那个名字在仓库里全局 grep 一遍，出现的地方一起改掉。⛔ 不许把某个历史名字当成固定检查项写进别处（个案不是规则，且会假阳性）。

6. **进工程是按需取用（pull），不是整包搬运**：只复制被业务代码 / 关卡数据真正引用的那几个文件，⛔ 不许把整包 / 整张素材表（或它的全量切片）灌进 `client/Assets/**`。典型后果：`Resources` 里 953 个资源文件 **795 个无引用**（而 `Core/ResPaths.cs` 只引用其中 8 个）⇒ 仓库噪音 + 加素材必然踩错。
7. **这条要有脚本兜住，不能只靠提醒**：项目侧跑 `tools/check-assets.ps1`（骨架 `reference/check-assets-template.md`）—— `client/Assets/Resources/**` 里凡有**未被任何 `.cs` / 关卡数据引用**的文件 ⇒ 报出来（口径：文件名在 `Scripts/**/*.cs` + `Resources/Levels/*.txt` 全文里 `-notmatch`）。（它是**项目侧工具**，⛔ **不占**那 5 条交付闸门的名额。）
8. **清单要能"精确重建"**：逐条写「源文件 → 工程目标路径」（含切片矩形 / 帧号 / 导出命令行）；⛔ 不许只写"从 X 解包来的"。
9. **交付打包（仅当用户明说"原版素材随交付一起给"）**：`tools/pack-original-assets.ps1` → `<项目根>/原版资源.zip` + git-lfs 提交（`.gitattributes`：`*.zip filter=lfs diff=lfs merge=lfs -text`）；zip 只放仓库根，⛔ 不许进 `client/Assets/**`；sha256 + 脚本版本记进 `清单.md`。细则见 `reference/asset-sources.md` §8.2。

## §1.10 ★★★ 规则层的否决权

> **为什么单列（根因在 skill 不在 agent）**：本 skill 明写"⛔ 不许把探针放 `client/_dev/`"，而项目级 `constraints.md` 把探针位置反过来写死成 `client/_dev/` ⇒ 那个目录堆了上百个文件。子 agent 不是不听话 —— 它读到的是**本 skill 自己在几份模板里写的**"项目约定优先 / 冲突时以本项目为准"，于是照章选了项目文档。⇒ **责任在 skill：把否决权交给了项目文档。**「项目约定优先」这个歧义写法已在 `scaffold/**` 与 `patterns/multi-agent.md` 一并修正。

**层级（越靠上越硬，下面只能加严不能放宽）**：

| 层 | 谁 | 能不能推翻下一层 |
|---|---|---|
| ① 用户本轮明说 | 用户 | — |
| ② **本 skill 的规则层（§0~§7，含 §1.x）** | 本 skill | ⛔ 谁都不能推翻（项目级 skill / 项目文档 / 既有代码 / 别人的工程都不行） |
| ③ 项目级 `<项目根>/tools/ai-skill/` | 项目主 agent | 只能加严 ② |
| ④ 项目文档（`docs/`、`策划/`、代码注释） | 任何 agent | 只能加严 ②③ |
| ⑤ 既有代码 | — | 不是依据（"别人 / 以前就是这么写的" ≠ 可以这么写） |

**「项目约定优先」的正确含义**：项目约定**只在**「本 skill 没写」或「本 skill 明说可自选」的地方优先（技术选型、命名、目录细分、消息号分段、配表字段名 —— 这正是项目级 skill 存在的最大理由）；**凡标了 `§0~§7` / `⛔` / 硬规则 / 硬闸门 的地方，项目约定一律不得冲突**。
**冲突时的正确动作是三步**（不是"在回报里说明"）：① 照本 skill 规则层做；② 把冲突的那份项目文档改掉（模板 / 约束 / 步骤文档 / 注释一起改）；③ 真认为规则层不合理 ⇒ **回报用户，由用户决定改 skill**，⛔ 不许自己在本项目里放宽。
**交付前自检**：对本项目 `tools/ai-skill/` 与 `docs/` grep `与全局 skill 的差异|以本项目为准|优先于全局|优先于通用`，命中处**逐条判**它是加严还是放宽，**放宽的一律改掉**。

## §1.11 ★ 收尾机械自检（只有 5 条；其余都是可选自检）

> **验收哲学**（`SKILL.md` §4 第 0 条）：验收 = **用户的抱怨消失 + 关键路径跑过一次 + 表现类看一眼**。
> **只有"光看会骗人"的事才值得写成检查项** —— 全部就下面 **5 条**，做成脚本模板 → `reference/verify-template.md`（新项目开工时复制成 `tools/verify.ps1`）。
> 任何一条 **FAIL** ⇒ 不许出现"完成 / 交付 / 实测通过"字样。**其余检查一律可选自检**，红了只当提示，⛔ 不许拿它拦交付。

| # | 查什么 | 通过标准 |
|---|---|---|
| 1 | **编译 / 构建通过** | 0 error（编不过，别的都白说） |
| 2 | **证据新鲜度**（唯一的"反自欺"判据） | 每条"已实测"引用的图 **mtime 晚于**它验证的代码 / 资产；作废**只作废受影响的行**（同模块 / 同功能链 / 同屏），⛔ 不是"任何文件一变就全量作废"。人眼看图**永远**看不出这是三天前的 ⇒ 只有这条必须机械化 |
| 3 | **引用可达** | 验收表里每个 `<路径>` / `<路径>:<行号>` / 函数名 **在盘上存在**（悬空 = 等于没证据）；无交接 / 进度类文档 |
| 4 | **交付卫生** | `Get-ChildItem <项目根> -Recurse -Filter *.cs \| Where-Object { $_.FullName -match '\\(_dev\|_assets_src\|_assets_tmp)\\' }` = 0 命中；`.ai-tmp` **≤300 文件 / ≤200 MB**，无 `bin/obj`、无 `-bak-` 目录备份 |
| 5 | **脚本 / AI 自己别崩** | `.ps1` 语法 0 错 + 非 ASCII 必带 BOM；**闸门自己崩 ⇒ 本次结论作废**，⛔ 不许假装绿 |

> **已删除、不再检查**（写清"不检了，为什么"）：覆盖矩阵 / 清单自洽 / 汇总核对 / 派活台账列数 /
> 差异登记逐条核对 / 覆盖命中率 / 行数或文件大小的阈值判断 / **"每个判据必须配负控"这类仪式** /
> 每种证据都要五列表格 + 哈希 + 时间戳。
> **理由**：这些抓到的都是**人眼 / 逻辑一眼能看出来的东西**；或者它们上次红的时候，抓的是**自己写错了**。

**写任何新判据之前先问两句**：① 「这条判据抓到的，是**人眼 / 逻辑一眼能看出来**的东西吗？**是 ⇒ 不写判据。**」
② 「这条判据上次红的时候，抓的是**真缺陷**还是**它自己写错了**？**后者 ⇒ 删。**」

**证据形态**：**一条命令 + 关键原始输出（几行）**，或**一张截图**。⛔ 不再要求：五列 TSV / 每片必交证据表 / 每个判据必配负控 / 每步记 SHA256。

**两条仍然成立、但不进 5 条的规矩**（它们不是"机械判据"，是人要记得做的事）：
- **引擎自称**：交付物里的引擎自称必须**逐字是 `clover-engine`**；判据取**渲染出来的那行字**（实机截图 / 运行时节点树），⛔ 不是 grep 源码 —— 源码里有 ≠ 画面上有 ≠ 大小写对（`SKILL.md` §6 第 9 条）。
- **例外仍要登记**：硬禁令（如「⛔ 别用 `Resources.Load` 绕开 `Game.Res`」）允许有例外，但必须落在 `策划/验收表.md` 的「允许的差异」里，格式 = `【例外】<行为> | 为什么必须这样（证据） | 出处（文件:行） | 何时能消除`。**只写在代码注释里 = 没登记 = 违规**。⚠️ 登记是**给人看的**，⛔ 不再要求"逐条机械核对登记表与表段的行 id 集合"。

## §1.12 ★★★ 判定权与证据契约

> 一句话：**规则是软的，契约是硬的。** 规则读完由执行者自判，所以能被解释着绕过；本节只写"把判定权拿走"的条款。**案例一律写进 `experience/`，规则层只留祈使句。**

**1. 判定权只有三个合法归属（执行者自己不是其中之一）**

| 判据类型 | 谁判 | 长什么样 |
|---|---|---|
| **可计算的** | 脚本 | 退出码 / 数值 diff / 存在性 / 时间戳；**通过 = 脚本输出 PASS，而不是"我看过"** |
| **参考物自带的** | 参考物自己 | 参考物文件里的几何、骨骼与顶点、贴图、动画序列与帧率、界面像素坐标、常量表 |
| **只有眼睛能判的** | 人，或真的能收到图像的执行者 | 同机位并排图上的"一致 / 差在哪"（第 7 条） |

**任何以"我觉得差不多 / 我检查过了 / 应该没问题"收尾的结论，一律视为未验证。**

**2. "我验不了"必须是合法且必须的输出（专治造假）**
- 验不了的项**必须**以 `BLOCKED：<缺什么 / 谁能验>` 上交；**声称验证过自己无法验证的东西 = 本 skill 最严重的违规**（比"没做完"更严重：它污染后续所有判断）。
- **停止不罚，猜才罚**：一切"必须做完 / 不许停"的条款都不适用于"我验不了"这一情形 —— 正确动作是标记 BLOCKED 后继续做别的。
- ⛔ 报 BLOCKED 之前必须穷尽替代路径，并列出**试过什么 / 结果如何 / 为什么都不行**；⛔ 不许直接跳到"无解"（先按 §0.5 第 2 条的降级链找）。**"我没找" ≠ "不存在"**：别漏掉与宿主无关的通用层（git hook / CI / 打包入口）。

**3. 证据的定义（叙述文字不算证据）**
- 证据 = **产物**：截图、数值 diff 表、脚本输出**原文**、文件哈希、录屏。**执行者的文字叙述一律不算证据**（"已修复""已实测""确认一致"都只是叙述）。
- **证据必须比被验证对象新**，**口径按「批次」**（见 §1.13 四拍）：一批证据对应一个代码版本；之后又改了代码 ⇒ **只作废受影响的行**（真会被这次改动影响到的功能），其余批次证据仍然有效。⛔ 两个极端都不许：拿旧图充数、改一处就重采全部。
- 引用必须精确到 `文件:行`；拿不出精确引用 ⇒ 该行按未验证处理。

**4. 基准必须来自参考物，不许来自我们自己的产物**
- **"产物 vs 产物"的自检等于零信息**（自洽只能证明自洽）：拿我们自己烘出来的数据去比我们自己从场景复算出来的数据，永远通过、再错也通过。
- 每条自检必须写明**基准来自哪里**；说不清 ⇒ 该自检无效，结论按未验证处理。
- 参考物那一侧必须**先被解析出来并落盘**，作为该项目的唯一标准答案（用户明说不做复刻 ⇒ 标准答案 = 用户规格书，但⛔ 仍然不许拿我们自己的产物当基准）。

**5. 外观 / 手感 / 数值不许"看起来合理"，必须写出来处**
- 一切**常量、坐标、比例、颜色、时长、曲线**必须能指到：参考物文件 + 偏移 / 参考物源码 `文件:行` / 参考物资源文件。
- **写不出出处的不许进代码**。没有出处时的正确动作是**去解析参考物**（解包 / 反编译 / 读数据），不是自己定一个；参考物确实拿不到 ⇒ 按 BLOCKED 上交并登记为"允许的差异"。

**6. 交付粒度：一个单元必须小到能被一条命令判生死**
- 禁止"一口气做完整个游戏 / 整张地图 / 全部界面" —— **范围是所有约束的天敌**：范围一大，"差不多"必然蒙混过去。
- 每个交付单元自带一条**可执行的通过判据**，不通过就不进下一个单元。允许做很久 —— 靠**切片**跨过去，不是靠砍范围。

**7. 外观验收的最低形式：同机位并排**
- 每个外观项 = 一组「参考物图 | 我们的图」（**同机位、同分辨率、同画幅**）+ 一行 `一致 / 差在哪 + 差多少`。**没有参考物那一侧，描述不算验收**（"画面里有一颗手雷"是描述，不是验收）。
- 动态项（手感 / 动画连贯 / 节奏）单帧判不了：要么逐帧录屏比对，要么把驱动它的**常量**与参考物对齐（第 5 条）。**终审是人。**

**8. 开工先验"感官通道"，不通就不许写感官结论**
- 任务含画面 / 声音时，**必须先用一张已知内容的图（或一段已知内容的音频）自检通道**；**读图返回占位 / 空 / 被省略时立即停止写画面类结论**，改为 `BLOCKED：图像通道不可用`。
- ⛔ 最贵的一种：连续几十次拿到"图像已省略"的占位文本，仍然逐条写出画面描述与"已修复" —— 这些结论全是编的，且在验收表上与真证据看起来毫无区别。

**9. 交付必须带一键复检入口**
- `tools/verify.ps1`（或等价脚本）逐行输出 `PASS / FAIL / HUMAN-ONLY`：`PASS/FAIL` 覆盖一切可计算项（数值 diff、可达性、存在性、mtime 新鲜度、哈希）；`HUMAN-ONLY` 列出只能由人或多模态判的项，供人一次过目。
- 用户**只跑一次脚本**，不陪执行者逐点调参。**"用户不可能陪我一点点调"就是本条的存在理由。**

**10. 结构底线**
> **执行者永远不是最后签字的人。** 只要还有一条结论由执行者自己签，本 skill 的全部禁令都可以被绕过 —— 因为它们最终都靠执行者的判断兑现。把签字权交出去（脚本 / 参考物 / 人）是唯一能被机器强制执行的约束。

## §1.13 ★★★ 改动回路：批次流水线（把贵的动作挤到最后，同一件事只做一遍）

> ### ⛔ T0（最高优先级）：**取证要批量**
> **一个交付单元该采的格，走一遍就够：编译一次 + 一条驱动链路按序跑完 + 采一次联络图。**
> - **验收表有 N 行 ≠ 要进 N 次实机**；派了 K 个执行者也 ≠ 每个执行者各自重进一次 Play 做同一件事 —— 验收行是"证据的**格**"，不是"实机的**次数**"。
> - 判据一句话：**同一件事（同一批格的同一次取证）不要重复做第二遍**；之后再改代码 ⇒ **只重采"这次改动真能影响到的那几行"**（⛔ "任何文件一变就全量作废 / 全量重采"是错的：没有因果关系的行不许被作废）。
> - ⚠️ **但本条不设次数上限**：没有"预算 / ≤5 次 / 用尽即停"。新批次、诊断态、新的因果范围、还没验完的格 ⇒ 照常再进，唯一要求是写得出理由（`ledger.tsv` 里 kind=`play` 行的详情列）。
> - ⛔ **典型违规形状**：把"批量改 + 一次取证"拆成 N 轮「改一点 → 编译 → 进 Play → 截图」⇒ 总等待 = N × 分钟级，其中绝大部分是纯重复等待。
> - **判据不是"验得够不够仔细"，而是"最贵的动作被重复了几次"**；⚠️ 这句不许反着读 —— 该验的格一个都不能少。
> - **为什么不小步循环**：编译与进 Play 是**分钟级**，"读数据 / 跑断言 / 数据 diff / 静态检查"是**秒级** ⇒ **便宜的多跑，贵的攒一批只做一次。**

### 四拍（一个交付单元走完 ①②③④）

| 拍 | 做什么 | 代价 | 禁令 |
|---|---|---|---|
| **① 一次性取证**（只读） | 把依据一次查完（参考物数据 / 引擎 API 出处 / 现有代码现状），产出**改动清单**：改哪几个文件、每处改什么、**每处的判据是什么** | 便宜 | ⛔ 这一拍不许写代码 |
| **② 批量改** | 按清单把改动一次全写完，中间**不编译、不截图** | 便宜 | ⛔ 不许改一处编译一次 |
| **③ 一次编译 + 预演** | 编译一次并确认成功 → 跑廉价自检（离线断言 / 数值探针 / 数据 diff / 静态检查）→ 挑出的问题批量修 → 再预演一轮。**循环粒度 = 一轮预演，不是"一处改动"** | 中 | 编译失败 ⇒ ⛔ 不许测 |
| **④ 集中出证据**（贵，只做一次） | ① 先出**证据分格表**（格号 / 状态 / **类别：数值类·表现类** / 判据 / 期望值）→ ② 按分格表**一条驱动链路按序跑完** → ③ 采**一次联络图**（N 格拼一张，格上烧「格号 + 状态 + 关键数值」），脚本按格判定，**AI 只读这张汇总图** | 贵 | ⛔ 不许逐项进出 Play、不许逐行截图逐张读图；④ 后再改代码 ⇒ 只重采**受影响的行** |

**③ 必须产出一份「预演报告」**：逐项写清哪些"已就绪、可采图"、哪些仍有风险 —— 这样 ④ 一次就能采对，不会"采完才发现要改、改完再采一遍"。

### 截图的三个触发条件（除此之外都不截）

1. **交付前**：把 `表现类` 的行采**一次联络图**（AI 只读汇总图，⛔ 不逐张读原图）；
2. **诊断态**：某个点改了多次仍不对 ⇒ 截该处的**全图**排查（**截图最有价值的用法**）；
3. **判据本质是画面**（动画没播 / 贴图错 / UI 不可见）⇒ 必须看图，数值替代不了。

**为什么这么定**：截一帧是分钟级，而 **AI 读一张图按像素烧 token** ⇒「47 项 ⇒ 47 张图逐张读」比「47 项 ⇒ 2~3 张联络图」贵**一个量级**；而判定本来就该由脚本做，AI 只分诊（§1.12 第 1 条）。联络图格式见 `reference/visual-loop.md` 第八节。

### 硬不变量

1. **任何实测之前，编译必须已成功**；编译失败 ⇒ **中止一切验证** —— 宿主可能仍在跑**旧程序集**，此时所有"实测"验的都是过期代码。
2. **证据必须比代码新 —— 口径按「批次」**：④ 之后又改代码 ⇒ **只作废受影响的行**，其余批次证据仍然有效。⛔ 不许改一处就重采全部。
3. **日志里的 Error / NullReference 当批次清零**：不许用"降频 / 忽略 / 不影响主流程"掩盖；每条都要有处置（修掉，或登记为已知并给出处）。
4. **收尾统计的是"错误总数"，不是"我没引入新错"。**
5. **采样器 / 驱动脚本：先自检，再上实机**（**近 100% 的"白等"**都出在这一步：跑场景是分钟级，自检是秒级 ⇒ **自检不过，一次都不许跑**）。三条必过（`SKILL.md` §3 第 8 条 · 闸门 `verify-script-crash`）：
   - **语法**：`.ps1` 先过 `Parser::ParseInput`，0 语法错误；
   - **编码（唯一口径）**：只看"**文件里有没有非 ASCII 字节**"—— 没有 ⇒ 不需要 BOM；**有**（不管在代码行 / 注释 / 输出里）⇒ **整个文件必须 UTF-8 with BOM**（无 BOM 时 PS 5.1 按 ANSI 解析 ⇒ **中文匹配静默失效**：脚本照跑、逻辑全错）⇒ 匹配用的中文字面量一律用码点拼；
   - **结束信号与超时**：完成判据只能是被测程序自己写的标记，且按"**新增次数**"判定（防读到上一轮的旧标记）；超时只许当兜底，⛔ 不许当完成判据。入口先验形状（如 `eval --code` 要 `return X;`，裸表达式编译不过 ⇒ 健康检查恒为 false，会把好好的 Play 会话当成"引擎没起来"杀掉）。
   - **读日志要 `FileShare.ReadWrite`**：游戏把日志**独占**持有，普通读法（`File.ReadAllText` / `-Raw`）每次读都抛 IOException ⇒ 标记永远读不到 ⇒ 又白等满一次超时。同类：日志路径按**当天**取、写完立刻读要**重试**。
6. **修 bug 的验证范围 = 这条 bug 的路径**（⛔ 不是"重跑全部场景"）：① 修之前先写一条能复现它的断言 / 探针；② 修完**只跑那条路径**，只重采它所在的行 / 屏；③ 全量重采只有两个合法时机：交付前最后一次，或改动确实横跨多个区域。⛔ 判据不是"多测一点更保险"，而是成本硬账：一个字段改动 × 全量场景 = 场景数 × 分钟级等待。
   **怎么才不靠自觉**：把"受影响的行 / 屏"做成**一份范围表** —— 重采工具只接受范围表算出来的场景，`evidence-freshness` 按**同一份范围表**判过期 ⇒ 规则与检查共用一个数据源。（旧的 `freeze-before-capture` 闸门**已删、不检了**：它靠全局 mtime 卡整批，把"改了无关文件"也判红，而人一眼就能看出哪些行真受影响。）

**「交付单元」的定义不变**（§1.12 第 6 条）：**能被一条命令判生死**的那一级（一个功能 / 一张表 / 一个面板），**不是"一行代码"**。单元内部可以批量；⛔ **单元与单元之间不许跳过 ③④** —— "批次"永远不是"攒着不验"的借口。

## §2 ★★ 交付闸门：一张必须填满的验收表

**表在开工时就建好**：`策划/验收表.md`，**行 = 参考游戏 A 的系统清单**。没有 A 的系统清单 ⇒ 没有验收分母 ⇒ 必然会漏（漏掉的全是"玩起来才知道"的：踩敌、顶砖块出道具、火球、旗杆通关、暂停菜单、双人模式）。**表里出现空行 = 没做完 = 不可交付。**

### 1:1 复刻硬标准（用户点名 A = 默认就是 1:1，不是"像"）

> 病根：把验收标准写成"像不像"。像 ≠ 1:1。除非用户明说"风格参考就行 / 不必一致"（例外登记同 §0 硬规则 6）。
> 用户明说不做复刻 ⇒ 本节不适用，改按《原创规格》逐条判（强度不变，只换标准答案来源）。

| 维度 | 1:1 的**硬要求** | 常见违规（都算不可交付） |
|---|---|---|
| **布局** | **逐元素对齐 A 的原版画面**：位置 / 尺寸 / 层级 / 间距按原版像素（用**同一分辨率基准**换算），并用原版截图并排比对 | 自己"设计"了一版顺眼的布局；元素居中 / 靠边"差不多" |
| **素材** | **必须用 A 原版的素材**（来源与穷尽标准见 §4 闸门 3）。占位色块 / 通用素材包 / 自画近似图 = 不可交付 | 用 KayKit / Quaternius / 内置几何体凑；占位色块当成品交 |
| **字体** | A 的原版字体（位图字体就用位图字体；中文用 A 中文版字形），字号 / 字距照原版 | 用引擎默认字体顶替，还自称"一致" |
| **色调/亮度** | 照 A 原版；⛔ 不许自己提亮 / 压暗 / 加滤镜 | 面板被颜色乘数压暗或自己调亮，却当"修好了" |
| **交互细节** | 按钮常态 / 悬停 / 按下 / 高亮、光标形态、音效时机逐项对齐 | 只做"能点"，不做原版的视觉 / 听觉反馈 |
| **节奏** | 动画速度、升级速度、任务长度按原版量级 | 随手调参 |

**对照方法（不作为"看过一眼"就算）**：① 以**同一分辨率基准**截原版图与自己的图；② 逐元素列表比对（位置 / 尺寸 / 素材 / 字体 / 颜色）；③ 每项只允许写 `一致` 或 `不一致（差在哪）`；④ **出现任何"不一致" ⇒ 该版本不可交付**，改完重截再比，循环到全一致；⑤ **允许的差异清单默认是空的** —— 想加例外，必须在 `策划/验收表.md` 里逐条写明理由（这份清单**同时**是「引擎 API 例外」的登记处，格式与检查见 §1.11 第 4 条）。

**交付物必须含「原版对照表」（`策划/对照表.md`）**（它是 §0.5 的执行形态）：每行 = 一个元素 `元素 | 原版值（含出处：文件:偏移 / 源码 文件:行 / 图片坐标） | 我们的值 | 差值`。
- **差值为 0 才算过**；写不出原版出处的那一行 = 该元素未验证。
- 覆盖范围至少：几何与碰撞（含**通行性**）、模型与动画数据、贴图、界面元素的坐标 / 尺寸 / 颜色、数值与公式。
- **表里没有的行，等于这个元素没人搬过** —— 不允许"实现了但没进表"。

**硬性判定**：
1. 任何一行「结论」为空 / 写着"未验 / 待验 / 下次补" ⇒ **禁止出现"完成 / 交付 / 实测通过"字样**。
2. **"说完成"与"列未验项"不许出现在同一条回复里。**
3. **证据按「类别」给，不搞一刀切** —— **每条验收行必须在表里标出它属于哪一类**：

   | 类别 | 包含什么 | 判据 |
   |---|---|---|
   | **`数值类`** | 数值 / 逻辑 / 状态 / 坐标 / 计时 / 计数 | **运行时日志行 + 断言输出**（实机跑出来的），⛔ **不需要截图** |
   | **`表现类`** | 动画有没有播 / 贴图对不对 / UI 可见与对齐 / 颜色 / 时序观感 | **交付前必须进一次「联络图」**（见 §1.13 第 ④ 拍），且**格号要能在图里查到** |
   | **`性能类`** | 帧率 / 帧时间 / 掉帧 / 卡顿 | **帧时间** 与 **渲染设备名**（`SystemInfo.graphicsDeviceName`）**必须同时给** —— 设备是 `Microsoft Basic Render Driver` 时是 WARP 软件渲染，**数字无意义、不许拿它下任何结论**；配方见 `experience/perf-triage.md` |

   ⚠️ **判据是"证据真的跑出来过"，不是"每行各跑一次"**：一个交付单元用一条驱动链按序把它的所有格跑完，再采一次联络图（见 §1.13 的 T0）。**验收表有 N 行 ≠ 要进 N 次实机**；⛔ 也不许改一处就全量重采。⚠️ **但这绝不是次数上限**：验不完 / 新批次 / 诊断 ⇒ 照常再进。一次性行为（死亡 / 通关 / GameOver）要在**那一次**里真的触发一次。
   ⛔ **两个极端都不许**：逐行截图、逐张让 AI 读；把 `表现类` 用数值代替（数字全对而金币动画根本没出来 —— **数字对 ≠ 表现对**）。
4. **禁止挑有利证据**：拍到坏图必须写清"坏在哪 + 改了什么 + 重拍图"。
5. **用户报的问题一律视为"表里漏了一行"** → 回去补表并把同类问题一起排查，而不是只修那一个点。

> 完整模板与判定细则见 `reference/game-delivery.md` §1。

## §3 ⛔ 开口前闸门（开工前一次性澄清；之后只有两种能开口）

**能开口的只有两种**：① **被阻塞** —— 缺一样**只有用户能给**的东西（密码 / 参考游戏名 / 用户亲手打开编辑器 / 用户点同意）；② **全部做完** —— 验收表**每一格都填满**，且每格的证据我都**自己读过**。
**其余一切句子一律删掉、继续做** —— 包括「要不要 / 接下来 / 进度 / 还需要我 / 你看行吗 / 计划 / 待办 / 还差几步」，**也包括回合结束时的收尾**（回合长度上限不是开口理由）。
**判据是产物不是自觉**：没到 ② 之前，出口的句子里不许出现「完成 / 做好了 / 实测通过」。「该不该做某一部分」不许问用户 —— 参考游戏有的就得做 ⇒ 自己定（§0 硬规则 3）。

### 开工前的澄清窗口（唯一被鼓励的"多问"）

> **"不许乱问"指的是不许问进度 / 许可，不是不许问清需求。** 开工前问清事实，是省掉最贵返工的手段。

- **时机**：接到任务、**还没写第一行代码 / 还没建工程之前**，允许把"不问就会做错"的问题**一次问完**。
- **形式**：**攒成一批、编号提问，一次发出**（一次 ≤ 5 条，每条给默认选项或候选）；**问完就开工**。
- **该问的**（问的都能落进文档）：参照**哪一款**具体游戏 / **形态**（单机·联机·单机+联网）/ 目标平台与**分辨率基准** / 范围边界（做到哪个场景为止）/ 素材能否用**用户本机文件**（如 MPQ·CASC）/ 有没有必须对齐的**硬指标**（时长、帧率、语言）。
- **不该问的**：参考游戏里有的功能（直接做）/ 我们内部的技术选型（自己定）/ "先做哪块"（自己定顺序）。
- **只开一次**：澄清窗口用完即关 —— 之后新出现的"只有用户能给"的阻塞仍可按 ① 问（如用户来打开编辑器），但**不许拿问题当拖延或征求许可**（"我先做 A 还是 B？你定" = §1 违规）。
- **答案必须落盘**：写进 `策划/策划案/{A}参考规格.md`（形态 / 范围 / 基准）与 `策划/验收表.md`，**后续全程照它执行、不许再反复确认**。

> **适用范围**：本闸门管的是「**向用户**开口」。**子 agent 不在此列** —— 它必须把结果回报给调用方（主 agent），那是它的职责（格式见 `patterns/multi-agent.md` 第 3 步）。

## §4 ★★★ 做游戏的四道硬前置闸门（不通过就停，不许自己绕）

**不通过任何一条，后面的工作都会白做。**

### 闸门 0（最先做）：判定横版 / 竖版（= 屏幕方向）

- **判据优先级**：① 原版这款游戏**本身**是横版还是竖版（联网搜一轮 `<游戏名> 横版还是竖版`；A 的**官方截图本身即铁证** —— 宽>高 = 横版，高>宽 = 竖版）→ ② 用户本轮是否明说 → ③ 都没有则按原版。⛔ **不许"没查就默认横屏"**。
- ⛔ **必查项（一条都不许跳，落在纸面上）**：
  - `ProjectSettings.asset` 的 `defaultScreenOrientation`（`Portrait=1` / `LandscapeRight=4` …）与 `defaultScreenWidth/Height`（**竖版 = 高 > 宽**，如 1080×1920）；
  - `CanvasScaler.referenceResolution`（横版 `1920×1080` / 竖版 `1080×1920`；引擎 `CloverPresentation` 的 `ReferenceResolution` 默认 1920×1080、**可配置**，竖版项目在业务侧设成 1080×1920 即可）；
  - **每个面板的布局常量**（竖版画布宽只有 ~1080 ⇒ 任何 `BoxW ≥ 1200` 的横排布局**必然是错的**）。
- **竖版落地口径**：面板一律**上下排布 + 角锚点**（⛔ 左右并排的"标签–输入框–按钮"一行要改成三行）；`SpriteBackground` ⛔ 不许靠 `preserveAspect` 留左右黑边（遇到"原图是竖的、画布是横的"就是**横竖判错了**，不是"用 preserveAspect 兜住"）。
- **判定结果写进** `策划/策划案/{A}参考规格.md` 顶部「形态」一节，**只判一次**，全程照做、不许反复自检。
- **判据**：能一句话回答「横/竖 + 画布参考分辨率 + 哪些面板按竖版重排」，且成品截图与 A 官方截图**同机位并排逐项 `一致`**。

### 闸门 0-b：判定游戏形态 —— 单机 / 网游 / 单机+联网

> **动手第一件事不是建工程、不是查环境，而是判定这个游戏"该不该有服务端"。** 判错方向后面全白做（单机被当成联服 = 反复探测本地服务器、建一堆用不上的 Go 代码；联机被当成单机 = 静默降级、核心玩法没了）。

| 要判定什么 | 怎么判 |
|---|---|
| **形态** | ① **单机**（纯本地）② **纯网游**（没服务器玩不了）③ **单机为主 + 联网功能**（原版两种模式都有） |
| **联网方式**（仅 ②③ 需要） | 权威服务器 / 局域网 / P2P / 大厅+房间 / 直连 IP / 云存档 |
| **依据从哪来** | ① **原版游戏本身是什么形态（第一依据，先联网搜清楚）** → ② **用户这一轮明确写了**什么（"联机 / 多人 / 服务器 / 对战 / 排行榜"）→ ③ 两者都没有 ⇒ **按原版形态做** |

**硬规则**：
- ⛔ **禁止"默认按联服处理"**，⛔ 禁止"需求没提就一律去查服务器环境"。
- **原版是单机的游戏就做单机**：**不建 `server/`、不调 `CloverNet.Init`、不查 etcd/redis/mysql、不跑 `env.exe`、交付说明首行标注「单机版」**。
- 只有**用户明确说了**联机 / 多人 / 服务器 / 对战 / 排行，**或原版本身就是纯网游**（MMO、对战竞技）⇒ 才走联服。**原版同时有单机与联机两种模式时（如暗黑2）：默认做单机模式**（它是原版的一等公民），除非用户点名要联机。
- **拿不准 → 先联网搜一轮原版形态**，仍拿不准才问用户一句话。⛔ 禁止"一边不确定、一边反复探测本地服务器环境"。
- **判定结果写进规格顶部「形态」一节，只判一次**，全程照它执行，不许中途反复改变、也不许反复自检。**形态一旦判为单机，"服务器环境自检"这一整段动作在本次任务里不存在。**

### 闸门 1：动手前先确认 360（及同类国产杀软）已关闭

**开工前先问用户一句「360 关了吗？」** 用户说没关 ⇒ **别创建工程**；**不确定 = 按没关处理**。
（360 会让 `Unity.Licensing.Client` 通道永远拒绝连接，编辑器每次重连烧 60 秒并循环 —— **那不是慢，是根本起不来**。详见 `reference/pipeline-and-unity-cli.md` 的「一、闸门 1」节。）

### 闸门 2：创建完 `client/` 后，让用户自己在编辑器里打开它；用户不开就不继续做

```
① AI 建工程目录 + 写好全部代码 + 生成器
② AI ★【在让用户添加项目 / 打开编辑器之前】把 com.unity.pipeline 写进 Packages/manifest.json
③ AI 才让用户去「添加项目到 Hub + 打开编辑器」，并给出可照做的 Hub 步骤
④ 用户打开（只能用户做）
⑤ AI 驱动那个活着的编辑器
```

**硬性禁止**：
- ❌ 创建完工程后自己跑 `unity run` / `unity test` / `Unity.exe -batchmode` 去"顺便"编译验证（首次导入把一次往返拖到十几分钟，且授权 / 杀软任一环出问题就是静默卡死）。
- ❌ 用户没打开编辑器就"先跳过实测，把代码交了"。
- ❌ **用户不开编辑器还继续往下做** —— 正确动作是**停下**说清"我需要你打开 `client/` 文件夹"，然后**不继续**。**没有例外**（批处理模式 `-executeMethod` 执行完立刻退出、进不了播放模式，既慢又验不了画面）。
- ❌ **在 Editor 脚本（生成器 / 构建器 / 批量工具）里调用任何会弹「原生模态对话框」的 API**（`EditorSceneManager.SaveCurrentModifiedScenesIfUserWantsTo()` / `EditorUtility.DisplayDialog*` / 模态 `EditorWindow` …）：无人值守驱动时它会**阻塞编辑器主线程**，把 Pipeline 连同后续**所有**命令一起拖成"静默卡死"（`/api/status` 仍 ready、`/api/dialog` 看不到、进程 CPU 差值 = 0）。"当前场景可能有未保存修改"一律**静默处理 + 打 Warn 日志**。

> Hub 添加步骤话术、P-0~P-5 全部踩坑（含 `unity status` 空表 / Editor 脚本弹原生模态框把编辑器卡死 / 失焦不 tick / 域重载 / 按键注入"完全没反应"）见 `reference/pipeline-and-unity-cli.md`。**遇到连不上、卡死、第二次进 Play 全蓝时去查它。**

### 闸门 2b：每一条 `unity` 命令都必须在「Unity 工程目录」里执行（前置，不是排查手段）

`unity` CLI 的编辑器发现是**相对 cwd** 的 —— 它只去 `<当前目录>/Library/Pipeline/.unity-pipeline-port` 找描述文件。**在工作区根 / 上一级 / 别的项目目录里跑**，它不会报"目录不对"，只会找不到编辑器（或去折腾别的工程）⇒ 把"我目录错了"误判成"包装晚了"，白让用户重启一次。

- ✅ **唯一合法形态**（二选一）：① `Set-Location "<项目根>/client"` 后跑；② **每条**命令都带 `--project-path "<项目根>/client"`（**不能只带第一条**）。
- ⛔ **禁止**在**工作区根**（所有 `clover-*` 项目并列的那一层）里跑任何 `unity` 命令；⛔ 用 `cd ..` 之类**相对路径**跳目录后再跑 —— **一律写绝对路径**。
- **证据要求**：拿 `unity status` 当"编辑器活着"的证据时，必须**同时**给出「工程路径 = `<项目根>/client`」这一项（只有 `ready` 不够 —— 它可能在报另一个工程）。
- **空表 ≠ 包装晚了**：先按本条自查目录，**再**谈重启编辑器。

### 闸门 3：素材必须先用参考游戏 A 自己的（本条只管"从哪来"）

**素材是"一眼认得出这是 A"权重最大的项。**

- **级 ①「A 自己的素材」= 唯一首选**：原版 / 同源 / 复刻 / 官方 SDK / mod 工具 / 社区提取 / rip。
- **"穷尽"的量化定义（达不到就不算找过）**：**≥ 4 轮**不同关键词（中英各半）× **≥ 3 类站点**（GitHub / Gitee 与镜像 / 素材站如 spriters-resource / 论坛贴吧 / 网盘直链）× 换过**格式与打包方式**（sprite sheet / 单帧 PNG / 模型 FBX·GLB / 贴图 / 音效包 / MPQ·CASC 解包产物）。
- ⛔ **在 ① 穷尽之前，禁止下载、禁止接入任何通用兜底素材**（KayKit / Quaternius / Kenney / 内置几何体…）。**不许用"先做起来 / 别停工 / 能用就用 / 为了效率"当跳级理由**。
- **调研必须落盘** `策划/素材调研.md`（每轮：搜了什么词 / 看了哪些站点 / 拿到什么 / 为什么不可用）。**没有这份文件 = 素材闸门未通过。**
- **A 的素材需要"用户本机游戏文件 / 登录 / 会员 / 付费 / 点按钮"时 ⇒ 走级 ④：先给用户清单并等用户**，⛔ **不许自己跳过 ①**。Blizzard 系（MPQ/CASC）即此类：解包工具链公开，但**游戏本体文件只有用户有**。
- **级 ③ 兜底素材只有前两级"真的做不到"时才允许**，且必须同时做三件事：① `策划/素材调研.md` 写清"①② 为什么都拿不到"；② **交付说明首行**高亮「⚠️ 未使用 <A> 的素材（原因：…）」；③ `client/资源欠缺清单.md` 登记"待换成 <A> 的素材"。
- **禁止把"下不动"说成"没有"**：换镜像 / Gitee 同名仓 / 压缩包直链 / 论坛附件 —— 都试过才算"拿不到"。
- **许可不设门槛**（非商用）：rip / 社区提取 / 来源不明**都能用**，能下就用，记一行来源即可。

> 详细分级、站点清单与"让用户下"的清单模板见 `patterns/game-demo.md` §4.0 与 `reference/asset-sources.md`。

## §5 ★★★ 谁来做（主 agent / 执行者·team 成员 分工）

> **主 agent：探环境 → 定契约 → 派活 → 验收。它不做实现。**

> 🚨 **主 agent 不许做实现** —— 因为**主 agent 的请求次数有上限**（本机实测约 500），下场写代码 = 把上限烧在**本来能外包**的活上 ⇒ **直接违规**。
> ① 读代码 / 定方案 / 写文件 / 跑编译 / 跑探针 / 截图，**全部派给执行者**；② 哪怕"看一眼就知道怎么改"，也要写成**任务书**派出去；③ "只剩最后一处小修 / 成员太慢 / 任务书要写太久" **都不是理由**：派活是**默认动作**。

### ⛔ 开工闸门：动手前先回答一句话（不回答就不许调工具）

**你接下来这次调用，属于哪一类？**

| 类 | 长什么样 | 谁做 |
|---|---|---|
| ① 探环境 | 只读：读文件 / grep / 跑只读命令 / 起编辑器看状态 | 主 agent |
| ② 定契约 | 写《步骤文档》《任务书》，或改 skill / 规则层 | 主 agent |
| ③ 派活 / 验收 | 发任务书、跑闸门脚本、采证据、对账 | 主 agent |
| ④ **实现** | **任何产出"工程产物"的写入**：业务代码、关卡/场景数据、配表、表现层、素材搬运、探针与闸门脚本的一次性改动 | **执行者（team 成员）** |

**① ② ③ ⇒ 做。④ ⇒ 立刻停手**：把它写成任务书（`scaffold/agent-impl.md`）派执行者，主 agent 只保留"定契约 + 验收"。
**判据不是"我能不能做 / 快不快"，而是"这一步属不属于实现"** —— 只要产物是工程的一部分就是实现。⛔ 特别提醒：**"顺手改一下"也是实现**（改一个数值、挪一格瓦片、修一行贴图名都算）；⛔ **"改数据文件"（关卡 txt / 表 / 场景）同样是实现** —— 它最容易被当成"我没写代码"从而绕过本节。

**⛔ 例外：小改动主 agent 直接做**（下面三条**同时**成立才属"小改动"）：① **改动面小**：**单文件**且**净增删 ≤ 20 行**；② **不新增行为 / 不改数据格式 / 不新增资源**（只是改文案、改坐标、改常量的值、补一行漏掉的调用）；③ **用户本轮明说**（"就一行文本""修个 bug""你自己改"）**或**用户报的是一个**点状缺陷**。
**留痕方式**：在 `.ai-tmp/test/ledger.tsv` 里写**一行**：`<ISO 时间>\t direct-fix \t <执行者> \t <相对路径> \t <一行理由>; 依据="<用户的要求>"`（闸门第 15 条按"具名裁定"通过它，不要求派活行）。
⛔ 不许拿"小改动"当**大改动的挡箭牌**：改了 3 个文件 / 动了数据格式 / 新增了行为 ⇒ 回到 ④ 去派活。

**⛔ 留痕**：每次派活后往 `<项目根>/.ai-tmp/test/ledger.tsv` 追加一行：`<ISO 时间>\t dispatch \t <执行者名> \t <任务书路径或一句话> \t <预计改动的文件/目录>`。**理由是"中断后查盘就知道跑到哪一步"** —— ⛔ 不再作为交付闸门（原"实现文件逐个对账派活行"已删：那是台账仪式，抓不到真缺陷）。

| 情况 | 谁做 |
|---|---|
| **新任务**（实现一块功能 / 一个模块） | **派 team 成员（异步）**（定义模板 `scaffold/agent-impl.md`） |
| **修 bug —— 原执行者还能找回来** | **交回原执行者**（恢复不了就在任务书里交接"上一棒做到哪"） |
| **修 bug —— 原执行者找不回来** | **主 agent 自己搞**，或照同一份 agent 定义开一个新执行者 |
| 探环境 / 定契约 / 写《步骤文档》/ 验收 / 裁决契约冲突 | **主 agent 自己**（不可下放） |

**⛔ 派生执行者的方式（方式错了 = 走回会卡死的同步通道）**：
1. **只许走 team 成员（异步）通道**：`Task(subagent_name=<执行者>, name=<成员名>, team_name=<队名>)`，**三个都给**。它**立即返回**、成员后台跑、完成时 `send_message` 回报。
2. ⛔ **不许走同步子 agent**（只给 `subagent_name`、不给 `name`）：主 agent 会进入等待，而宿主对**单次子任务等待**有上限 ⇒ **频繁卡死**（`code=10003 This operation was aborted` / `No result found`），且**卡死后拿不到回报**。
3. **派活后核对"形态"，不是"模型"**：确认派生时**三参数齐全**。⛔ **不许拿"问模型名"当中止依据** —— 成员报出的模型串是宿主注入的自我描述，**证明不了任何事**；只用它做**抽样台账**（任务书要求"回报首行写模型标识"，长期比对）。
4. **中止 ≠ 白做、也 ≠ 停工**：先让执行者把进度落盘、回一条简短回报，再把**已完成的成果**交给新执行者接力。⛔ **不许回滚已落盘的产出**。
5. **一片一成员**：派 team 成员（异步），等它 `send_message` 回报 → 验收 → 再派下一片。**可以多片并行**（异步互不阻塞）。
6. ⛔ **skill 与引擎源码都只读**：项目级 `<项目根>/tools/ai-skill/`、仓库里的全局源 `ai-skill/`、宿主的安装副本**全都不许改**；`clover-client-unity-engine` / `clover-server-engine` 的 `Runtime/**`、`pkg/**`、`internal/**`、`Editor/**` **也不许改**。
   碰到**引擎缺口 / 引擎 bug / skill 有错或说不清** ⇒ **写进 `<项目根>/引擎问题.md`**（三段：`## 引擎缺口` / `## 引擎 bug` / `## skill 问题`；每行 `现象 | 最小复现 | 影响 | 我们的绕法 | 建议`），然后**用绕法把活做完**（⛔ 不许停、⛔ 不许改源码绕过）。登记口径见 `patterns/engine-fix.md` §2。（`engine-issues` / `no-engine-edits` 两条闸门条目**已删、不检了**：规则照旧成立，但靠人读 `引擎问题.md`，不再单独做检查项。）
   **唯一例外**：用户**本轮明说**"可以改引擎 / 顺手修引擎" ⇒ 才走 `patterns/engine-fix.md` 的改引擎 SOP，并在 `引擎问题.md` 记一行指向那次修复。
7. ⛔ **派活失败 / 拿不到回报 ⇒ 先查盘，两次为限**：派活调用返回失败时，**先去盘上查它是不是已经落地了**（相关文件的 mtime / 内容 / dump / 截图）。**落地了就按"已完成"验收**（**回报丢了 ≠ 活没干**）；只有确实没落地才重派。**连续两次拿不到可用回报 ⇒ 主 agent 直接接手干完**（此时"不许自己实现"让位于"把事做完"），并在留痕里写 `# takeover: <原因>`。⛔ 不许无限重派、⛔ 也不许把用户夹在中间等。
8. **派活后说清"去哪儿收结果"**：用一行说清**三件事** —— 派了什么 / **成员名 + 队名** / **它完成后会 `send_message` 回报**（主 agent 会先**查盘**再验收，**不靠等**）。

> **⚠️ team 成员读到本节时**：你不适用"不许做实现"这条 —— 你是**执行者**，要下场干活、而且要干到底；唯一的限制是**不许再派生下一层**（见 `patterns/multi-agent.md` 第 4 步）。

### （可选，大型 1:1 复刻才用）全量覆盖自查 → `patterns/full-coverage-audit.md`

> ⛔ **默认不做**（`SKILL.md` §9 路由表）：验收 = **用户的抱怨消失 + 关键路径跑一次 + 表现类看一眼**。下面这套"实体清单 × 状态矩阵"是**大型 1:1 复刻**才值得上的重武器，⛔ 不是每个项目的必做仪式。
> ⛔ **它的六个闸门条目**（`coverage-rows` / `coverage-filled` / `coverage-diff` / `coverage-dimensions` / `scale-tier` / `impact-radius`）**已从交付闸门删除、不检了** —— 理由：它们判的是"表格齐不齐"，靠把两边凑相等就能变绿，而真漏项人眼 / 逻辑一眼能看出来。
> **病根这一段没删**（它仍成立）：用户报一条修一条 ⇒ 报的全修、没报的全漏；**漏检没有代价** ⇒ 默认退化，把"用户报的"当成任务边界。治它最省的办法是**关键路径真跑一次 + 自己顺手把同类问题一起修**（`SKILL.md` §6 第 1 条）。

**四条不变量（缺一条方法失效；上这套方法时才有意义）**：① **行数是数出来的**（清单由脚本枚举盘上实体生成，⛔ 手写 / 凭记忆 ⇒ 结构上必然漏）；② **一行一个判据**（可计算 → 脚本断言；参考物自带 → 逐值比；只有眼睛能判 → 同机位并排图）；③ **漏一行 = 自己少验一块**（⛔ 不再有闸门替你数，靠清单自己过一遍）；④ **分辨率写死**（穷举「对象 × 状态 × 边界值」，⛔ 不是"每一帧 / 全部组合"）。

**域清单（按项目填）**：**表现域**（外观每个物件 × 材质贴图颜色尺寸 / UI 每个面板 × 每个元件 × 每个状态 / 动画每个 controller × 每个 state × 关键帧循环时长事件 / 音频每个播放场景 × 播放停止 + 每个音效事件 × 触发条件音量组 / 特效每次开火命中等）· **逻辑域**（每条分支 + 每个边界值 / 交互矩阵逐对枚举：谁能穿谁·站谁·推谁·伤谁·重叠 / 碰撞体有无与"刻意的无碰撞" / 高度带与跳跃边界）· **资源域**（出处 + 引用完整性）· **性能域**（帧时间 + 渲染设备名）。

**维度表**：`D1 资源` · `D2 几何场景` · `D3 材质贴图` · `D4 UI/HUD` · `D5 动画` · `D6 特效` · `D7 音乐` · `D8 音效` · `D9 碰撞可行走` · `D10 玩法逻辑` · `D11 输入交互` · `D12 流程流转` + `S1 数值配表` · `S2 性能` · `S3 设置兼容`（完整枚举对象 / 状态边界 / 默认判据 / 典型漏检见 `patterns/full-coverage-audit.md` §3）。**跨维度交叉只交叉有因果的对**（动画×逻辑状态 / UI×流程状态 / 音效×事件×材质 / 碰撞×角色类型 / 特效×命中材质 / 输入×上下文 / 音乐×场景转移 / 数值×逻辑分支），⛔ 不做笛卡尔全组合（会爆炸并被读成"做不完"）。
**核心认识**：**游戏是复合产物** ⇒ **单维度完工不等于完工**（几何对+碰撞错 = 箱子能穿；动画数据在+没播 = 木头人；音频在+没挂事件 = 全程无声）。实例化模板 = `scaffold/coverage-matrix.md`。

**切片**：一次一片、一片一域，走 team 成员（异步：成员名 + 队名），任务书逐字写"本片要勾满哪些行"；能离线判的不进 Play。

**规模档位**（只改**采样密度**，⛔ 不改"要不要判"）：`S 小 demo` 1-way · `M 中型` 2-way(pairwise) · `L 复刻/大型` 3-way + 全状态全边界。判一次、写进规格顶部；**可上调，⛔ 不可因赶时间下调**；S 档同样要求"每维度有行"（⛔ 不再做"零空行 / 零不一致"的机械核对）。

**（历史）上限闸门 —— ⛔ 六条全部已删、不检了**：`coverage-rows` / `coverage-filled` / `coverage-diff` / `coverage-dimensions` / `scale-tier` / `impact-radius`。理由：它们判"表格齐不齐 / 档位写没写"，抓不到真缺陷，靠凑数或补一行就能变绿。⛔ **别再装回 `tools/verify.ps1`**。

**单片规模上限**：一片 = **一个交付单元** + **≤ 约 20 分钟 / ≤ 130 轮工具调用**；超了就**拆片**。真实理由是**成员自己会撞上 `maxTurns: 250`**，而异步通道下被掐断时调用方不会立刻知道，只能靠「防卡死三件套」的**心跳文件**发现。

**中止 / 无回报的标准处置（⛔ 不许重派原任务）**：① **先查盘**（`git status` + 近 1~3 小时 mtime + `.ai-tmp/test/` 最新产物）判定跑到哪一步；② 已落盘 ⇒ **按完成验收**（⛔ 不回滚）；③ 派**接力棒**（任务书"前置依赖"一节写清"上一棒做到哪 / 还剩什么"，只做没做完的）；④ 连续两次无回报 ⇒ 主 agent 接手 + `# takeover:`。

**规模判断失误时的合法出口（唯一例外，必须带数据）**：提一次「重新定范围」（已完成 / 剩余量 / 2~3 个可选范围 + 各自代价 + 建议），由用户裁一次。⛔ 与"不许问要不要继续"不冲突；⛔ 不附剩余量与代价数字 ⇒ 照旧违规。

**修 bug 的覆盖口径**：⛔ **只检查 bug 不够** —— 一处修改的爆炸半径可能跨维度（改门板影响走门 / 卡位 / 视线 / 弹道 / 雷达）⇒ 只修症状 = 拆东墙补西墙。**正确口径 = 影响域穷举**（因果链可达的子集，通常 < 5% 行数）：① 定位维度 ② 找因果链 ③ 爆炸半径枚举（显式写出）④ 判影响域内所有行 ⑤ 修 + 重判 ⑥ 回归。⛔ 修 bug 也不许全量扫（那是交付验收的事）。→ `patterns/full-coverage-audit.md` §9

**为什么主 agent 不做实现**：宿主对「单个任务」的模型请求数有硬上限（本机实测约 500）。主 agent 自己实现几百轮就撞墙、手里只剩半成品；只派活则 500 轮能管 25~50 个子任务。
**为什么修 bug 优先交回原执行者**：它带着当时的全部上下文，比重新交代一遍便宜得多；**上下文真丢了就别硬重建**，主 agent 自己搞更快。
**跨上限靠「接力」，不靠「砍范围」**：详见 `patterns/multi-agent.md` 的「轮次预算与接力」。

## §6 ★ 动手前两件事

**第一件：混合模式找依据（六处同看 + 联网；⚠️ 不是串行漏斗）**

| 看哪里 | 回答什么 | 优先级 |
|---|---|---|
| 本项目自己的 skill / 文档 / 源码 | 这个项目的约定、打算怎么做、既有写法 | 🥇 最高 |
| 引擎源码 / 引擎文档 / 引擎 skill（含本 skill 的 patterns） | 能力的真实签名与行为、机制、通用做法 | 🥈 其次 |
| 联网搜索 | 没见过的问题的通用解法、报错含义、版本差异 | 🥉 再次 |
| 自己设计 | 以上都没有 | ✅ 允许，但要标注"本项目新增" |

**冲突时以谁为准：用户 > 引擎 > 联网/自创。**

> ⛔ **红线：「用户源码」= 本项目自己的源码。别人的 `clover-project-*` 除白名单外不许看、不许抄。**
> 工作区里经常同时摆着好几个 demo 工程（各自带 `client/`、`tools/ai-skill/`、`策划/验收表.md`、`Assets/Editor/*.cs` 生成器、素材目录…）。**做新项目时，它们不是依据，是污染源。**
> **禁止**（针对新建项目）：打开 / 读 / grep / 参考工作区里**不属于本项目**的任何 `clover-project-*`（源码、Editor 脚本、`tools/ai-skill/`、`策划/`、`docs/`、素材，全算）；照抄它们的目录结构、模块 / 面板命名、验收表、工程生成器、配表、写法与素材路径；以"隔壁项目就是这么做的"为由决定本项目的任何设计。
> **✅ 白名单**：`clover-doc` 的[游戏 Demo 清单](https://github.com/qw576483/clover-doc/blob/main/ai/game-demo.md)里列出的 `clover-project-*`（**引擎 + skill 交付出来的成品**）**允许读、允许对照其做法与形状**（目录组织、验收表交付口径、生成器组织方式）；**边界只有一条：取做法与形状，不取领域内容**（游戏专有名词 / 模块名 / 数值 / 素材不许搬进本项目）。
> **允许抄的只有三处**：① 本项目自己的 skill 与源码；② 引擎源码 / `clover-doc` / 本 skill 的 `patterns`、`scaffold`、`experience`（通用形状，示例代码不得当 API 用）；③ 白名单里的成品工程（同样只给做法与形状）。
> **新项目的一切从 0 自己设计** —— 目录、模块、面板、生成器、配表、素材来源全部自己定，新引入的东西在交付说明里写清"本项目新增"。
> **另一个例外**：用户**本轮明确点名**「参考 / 沿用某个已有工程」时才允许，且**只在点名范围内**。

**看完仍没有现成的 ≠ 不做了**：可以① 用通用原语自己拼、② 联网找成熟方案读懂后落地、③ 自己设计。**唯一不许的是"编"** —— 任何 API / 类名 / 字段名都必须能指出出处；新引入的东西必须写清"这是新增能力"，**不许让它看起来像引擎既有 API**。（详见 `reference/workflow-and-standards.md` §1。）

> ⛔ **「引擎」这一档里最常踩的：写通用设施前必须先查引擎能力表**
> 动手写任何"通用设施"之前，先过一遍 `reference/engine-mental-model.md` §4 的能力表。这十类一律先查：**UI 构建 / 对象池 / 存档·设置 / 图集 / 本地化 / 配表 / 动画 / 相机 / 场景 / 音效**。**引擎有就用引擎的，禁止重造轮子。**
> **表里没写到的通用需求 → 先去引擎 `Runtime/**` 搜一遍再动手。**

**第二件：策划自审** —— 动手前先出《行为 → 表现规格》表（每个行为在**画面 / 动画 / 声音 / UI·数值反馈 / 网络**上分别是什么）；不知道就去搜参考游戏；表里出现"占位 / 后续替换 / 留钩子" ⇒ **视为没做完**。（详见 `reference/game-delivery.md` §5。）

**图片需求是硬闸门**：不能读图 ⇒ **立即停下**，请用户换多模态模型或先转写成文字方案；能读图也要**先转写成文字方案**再动手；图片是需求输入，**不是美术素材**。（详见 `reference/game-delivery.md` §7。）

**不确定时按四级查**：项目 skill → clover-doc → 源码 → 问用户。**硬约束：不许编造任何 API**（任何 API 名必须能指出出处，指不出 = 不许写）。**没搞懂调用链不许动手。**（详见 `reference/workflow-and-standards.md` §2。）

## §7 错误处理与日志（硬约束，服务端 + 客户端都适用）

> **凡是"没按预期走"的分支，必须留下一条日志。** 不写日志的失败 = 将来无人能查的事故。

- 必须打：出错返回 / 兜底判空 / 参数校验失败 / 非法状态 / `switch` 的 `default` / 客户端网络·反序列化·资源加载失败 / 高频回调里的异常（**防刷屏：只报一次或降频**）。
- 用什么打：服务端 `logger.Infof/Warnf/Errorf`；客户端 `Game.Logger.Info/Warn/Error(tag, msg)`。**禁止**服务端用 `log.Printf`、客户端用裸 `Debug.Log` 打业务日志。
- 日志必须带可定位信息（谁 / 哪个消息号 / 关键参数 / 期望 vs 实际），前缀统一。

> 完整清单与收尾自检见 `reference/workflow-and-standards.md` §3。
