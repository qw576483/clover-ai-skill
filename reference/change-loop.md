# 改动回路（四拍批次 / T0）— 细节展开

> 规则层入口 = `reference/rules-full.md` 的「改动回路：批次流水线」（§1.13）。本文件只写**规则层没展开的细节与判据**。

## ⛔ T0：取证是一次性的批量动作

**一个交付单元（= 能被一条命令判生死的那一级）只许走一遍**：编译一次 + 一条驱动链路按序跑完 + 采一次联络图。

- **验收表有 N 行 ≠ 要进 N 次实机**；**派了 K 个执行者也 ≠ 每个执行者各自进一次 Play** —— 验收行是"证据的**格**"，不是"实机的**次数**"。
- 判据一句话：**凡"分钟级"的动作（编译 / 进 Play / 截图 / 跑生成器 / 出资产），在一次交付里只许做一次**；之后再改代码 ⇒ **只重采"这次改动真能影响到的那几行"**（⛔ "任何文件一变就全量作废"是错的）。
- ⛔ **典型违规形状**：把"批量改 + 一次取证"拆成 N 轮「改一点 → 编译 → 进 Play → 截图」⇒ 总等待 = N × 分钟级，绝大部分是**纯重复等待**。
- ⚠️ 本条**不是**让你少验：该验的格一个不少，改的只是**顺序与粒度**。
- **为什么不小步循环**：编译 / 进 Play / 藏键抢拍都是**分钟级**，而"读数据 / 跑断言 / 数据 diff / 静态检查"是**秒级** ⇒ **便宜的多跑，贵的攒一批只做一次**。

### 四拍（一个交付单元走完 ①②③④）

| 拍 | 做什么 | 代价 | 禁令 |
|---|---|---|---|
| **① 一次性取证**（只读） | 把依据一次查完（参考物数据 / 引擎 API 出处 / 现有代码现状），产出**改动清单**：改哪几个文件、每处改什么、**每处的判据是什么** | 便宜 | ⛔ 这一拍**不许写代码** |
| **② 批量改** | 按清单把改动**一次全写完**，中间**不编译、不截图** | 便宜 | ⛔ 不许改一处编译一次 |
| **③ 一次编译 + 预演** | 编译**一次**并确认成功 → 跑**廉价自检**（离线断言 / 数值探针 / 数据 diff / 静态检查）→ 一轮预演里挑出的问题**批量修** → 再预演一轮。**循环粒度 = 一轮预演，不是"一处改动"** | 中 | 编译失败 ⇒ ⛔ 不许测 |
| **④ 集中出证据**（贵，**只做一次**） | ① 先出**证据分格表**（格号 / 状态 / **类别：数值类·表现类** / 判据 / 期望值）→ ② 按分格表**一条驱动链路按序跑完** → ③ 采**一次联络图**（N 格拼一张，格上烧「格号 + 状态 + 关键数值」），脚本按格判定，**AI 只读这张汇总图** | 贵 | ⛔ 不许逐项进出 Play、不许逐行截图逐张读图；④ 后再改代码 ⇒ 只重采**受影响的行** |

**③ 必须产出一份「预演报告」**：逐项写清哪些"**已就绪、可采图**"、哪些仍有风险 —— 这样 ④ 一次就能采对，不会"采完才发现要改、改完再采一遍"。

### 截图的三个触发条件（**除此之外都不截**）

1. **交付前**：把 `表现类` 的行**采一次联络图** —— AI **只读这张汇总图**，⛔ 不逐张读原图；
2. **诊断态**：某个点**改了多次仍不对** ⇒ 截该处的**全图**排查（**这是截图最有价值的用法**）；
3. **判据本质是画面**（动画没播 / 贴图错 / UI 不可见）⇒ 必须看图，数值替代不了。

**为什么这么定**：截一帧是**分钟级**，而**AI 读一张图按像素烧 token** ⇒「47 项 ⇒ 47 张图逐张读」比「47 项 ⇒ 2~3 张联络图」贵**一个量级**；而**判定本来就该由脚本做**，AI 只分诊。联络图的格式、采集与判定规范见 `reference/visual-loop.md` 第八节。

### 五条硬不变量（细节）

1. **任何实测之前，编译必须已成功**；编译失败 ⇒ **中止一切验证** —— 宿主可能仍在跑**旧程序集**，此时所有"实测"验的都是过期代码。
2. **证据必须比代码新 —— 口径按「批次」**：④ 之后若又改代码 ⇒ **只作废受影响的行**，其余批次证据仍然有效。两个极端都不许（拿旧图充数 / 改一处重采全部）。
3. **日志里的 Error / NullReference 当批次清零**：不许用"降频 / 忽略 / 不影响主流程"掩盖；每条都要有处置。
4. **收尾统计的是"错误总数"，不是"我没引入新错"。**
5. **采样器 / 驱动脚本：先自检，再上实机**（**近 100% 的"白等"**都出在这一步：跑场景是**分钟级**，自检是**秒级** ⇒ **自检不过，一次都不许跑**）。四条必过（代码与闸门见 `reference/verify-template.md` 第 14 项）：
   - **语法**：`.ps1` 先过 `Parser::ParseInput`，**0 语法错误**；
   - **编码**：`.ps1` 要么**纯 ASCII**，要么**带 BOM**。无 BOM 且含 CJK 时 PS 5.1 按 **ANSI** 解析 ⇒ **中文匹配静默失效**（脚本照跑、逻辑全错 ⇒ 白等满超时）⇒ 匹配用的中文字面量**一律用码点拼**；
   - **结束信号与超时**：完成判据**只能是被测程序自己写的标记**，且按"**新增次数**"判定（防读到上一轮的旧标记）；**超时只许当兜底，⛔ 不许当完成判据**。入口先验形状（如 `eval --code` 要 `return X;`，**裸表达式编译不过** ⇒ 健康检查恒为 false，会把**好好的 Play 会话**当成"引擎没起来"杀掉）；
   - **读日志要 `FileShare.ReadWrite`**：游戏把日志**独占**持有，普通读法（`File.ReadAllText` / `-Raw`）**每次读都抛 IOException** ⇒ 标记永远读不到 ⇒ **又白等满一次超时**。同类：日志路径按**当天**取、写完立刻读要**重试**。
6. **修 bug 的验证范围 = 这条 bug 的路径**（⛔ **不是"重跑全部场景"**）：① **修之前先写一条能复现它的断言 / 探针**；② 修完**只跑那条路径**，并**只重采它所在的行 / 屏**；③ **全量重采只有一个合法时机**：交付前最后一次，或"改动确实横跨多个区域"。判据不是"多测一点更保险"，而是**成本硬账**：一个字段改动 × 全量场景 = **场景数 × 分钟级等待**。
   **怎么才不靠自觉**：把"受影响的行 / 屏"做成**一份范围表**（`reference/verify-template.md` 第 6 项的 area/panel 映射**就是**这份表）—— **重采工具只接受范围表算出来的场景**，闸门第 6 条按**同一份表**判过期 ⇒ 规则与检查共用一个数据源。

**「交付单元」的定义不变**：**能被一条命令判生死**的那一级（一个功能 / 一张表 / 一个面板），**不是"一行代码"**。单元内部可以批量；⛔ **单元与单元之间不许跳过 ③④** —— "批次"永远不是"攒着不验"的借口。
