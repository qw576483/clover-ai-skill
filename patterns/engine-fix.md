# 改引擎 SOP（有 bug 就改引擎，不再问用户）

> **前提（硬性）**：用户已明确「牵扯到引擎 bug 就顺手修复」。因此遇到引擎缺陷时
> **默认就是修引擎**，不要再反问"要不要改引擎"；只有**改动量级大 / 会破坏现有 API 兼容 /
> 需要改协议**时才回头找用户确认方案。

---

## 0. 三条铁律

| # | 铁律 |
|---|---|
| 1 | **先证明是引擎的 bug**：读源码 + 写一个**最小复现用例**（跑起来就是失败/死锁/超时），再动手。**不许**"看着像 bug 就改" |
| 2 | **最小修复**：只改必需的行，不顺手重构、不动无关文件、不改公开签名（除非用户同意） |
| 3 | **修完必须自证**：引擎全量 `go build` + `go vet` + **跑复现用例**（修复前失败 → 修复后通过）+ 业务侧端到端复跑 |

---

## 1. 定位：从"现象"走到"那一行"

| 现象 | 怎么定位 |
|---|---|
| 客户端收不到某类事件 | 从**消费端**回溯：客户端 `Runtime/**/*.cs` 的解析入口 → 消息号 → 服务端推送点。例：客户端只认 `EPushDataSync(4003)` 且外层 key=事件名 ⇒ 服务端有没有按这个形状推？ |
| 服务端逻辑"跑了但没效果" | 找到产出点（如 AOI 产 `viewPush`）→ `grep` 它的**订阅者**；**没有订阅者 = 事件进黑洞**（本仓真实踩过：`viewSubject` 只有索引更新，快照被丢弃） |
| 死锁 / 卡住 / 超时 | 看**锁的作用域与回调时机**：持锁期间是否调用了会**同步回调**你的函数（本仓真实踩过：持 `viewMu` 调 `grid.EndBatch()`，而它同步回调 `onViewChange` 去拿同一把锁 ⇒ `Enter/Move/Leave` 必然死锁） |
| 偶发/时序问题 | 用**高频日志**先看真实顺序（首次全量 + 之后每 N 次，见 §3），不要靠猜 |

**判定标准**：能一句话说清「谁调用谁、在哪一行断掉」。说不清 → 继续查，别改。

## 2. 修：三种典型修法（本仓已验证）

| 类型 | 症状 | 修法 |
|---|---|---|
| **事件无消费者** | 产出方明明算好了，客户端永远收不到 | 补下发：在消费点按**客户端真实解析格式**推送（消息号 + 外层 key 必须严格对齐，否则客户端静默丢弃） |
| **可靠性选错** | 位置增量用不可靠没问题，但**进/出视野是不可重建状态**，丢一条客户端永远不知道实体存在 | 语义分级：不可重建状态走 `Reliable`；只有可重建的高频增量才 `BestEffort` |
| **锁顺序 / 自锁** | 必然死锁，且往往"以前没跑过所以没发现" | 明确锁边界：**回调期间不持锁**；把"窗口锁"与"数据锁"拆开（`batchMu` + `viewMu`） |

## 3. 日志纪律（引擎侧）

- 高频路径**必须防刷屏但不能静默**：`首次全量 + 之后每 N(如 1000) 次一条`。
- 失败必须带**可定位信息**：事件名/对象 id/路径/期望值；用 `logger.Warnf/Errorf`，禁止标准库 `log`。
- 客户端侧用 `Game.Logger.Info/Warn/Error(tag, msg)`；拿不准时 `?.`。

```go
// 引擎侧高频失败日志范式（本仓 entitysync.go 用的就是这个）
var failCount atomic.Uint64
func viewPushFailf(format string, args ...any) {
    n := failCount.Add(1)
    if n == 1 || n%1000 == 0 {
        logger.Warnf(format+" (累计 %d 次)", append(args, n)...)
    }
}
```

## 4. 回归用例：为缺陷补一条"跑的起来"的证明

> 本仓约定：**新功能不写单测**，但**为真实缺陷补复现用例属于排查手段，不算写单测，且必须补**。

写法要点：

1. 用例必须**先失败**（修复前跑出超时/失败），再在修复后**通过** —— 这是"真的修了"的唯一证据；
2. 用**真实链路**而不是 mock：起真实存储/发布订阅，断言**最终可观测结果**
   （例：断言"watcher 在 `EPushDataSync` 上收到了 `{"enter":{"entity_id":N}}"`"）；
3. 带**超时**（`go test -timeout 90s`），避免死锁类缺陷把 CI 挂死；
4. 文件命名 `*_test.go`，注释写清「复现什么缺陷、修复前什么现象、修复后什么断言」。

```bash
# 引擎侧验证三连
cd <engine>; go build ./... && go vet ./...
go test ./internal/domain/<模块>/ -run <你的用例> -v -timeout 90s
```

## 5. 记录：写进**引擎源码注释 + 回归用例** —— **不另建台账**

> ⚠️ **落点只许是引擎仓库**：缺陷的根因 / 最小复现 / 自证写在**受影响代码的注释**里，并配一条回归用例（§4）。
> **引擎改动影响所有项目**；说明塞在业务 demo 目录里 ⇒ **下个项目看不见 ⇒ 同一个坑被反复踩**。
> 业务项目的 `constraints.md` 只放**项目自己的**约束 + "本项目依赖了哪一处引擎修复"的一行指引 ——
> 指引写**文件 + 方法名**（可达、可直接跳转）；⛔ 不写编号、⛔ 不指向引擎仓库的某个 md。
> （旧版本文档写过"落到 `<项目根>/tools/ai-skill/constraints.md`"**那是错的**；
> 也**不再**有"在引擎仓库集中登记一份 `修复记录.md`"这一步 —— 该台账已删除，编号体系随之作废。）

### ★ 改引擎不是只改代码 —— 这两件必须一起做

1. **同步更新引擎侧文档与注释** —— 落点是**三处**，一个都不能漏：

   | 落点 | 改什么 |
   |---|---|
   | `Runtime/**` 源码注释 | 受影响的类/方法注释。**公开之后原注释若还写着"业务不直接使用"就是错的。** |
   | 引擎仓库内的 `clover-client-unity-engine-index.md` / `结构规则.md` | 与本次改动相关的段落 |
   | ★ **站点文档 `clover-doc/`** | **给人看的权威文档**：`client/development/*.md`（对应模块那篇，**API 参考表 + 常见问题**通常各要补一处）、`client/reference/api-cheatsheet.md`（新 API 登记）、`client/reference/constraints.md`（属于"坑/约束"的） |

   **文档与代码打架 = 下一个人照着文档写出错的东西。**

2. **同步更新本 skill**：若改动改变了"业务该怎么写"（新增 API / 语义变化 / 新坑），
   改 `reference/` 对应文件（`engine-mental-model.md` 的能力表与静默失败清单、
   `client-modules.md`、`unity-cli.md` 等）。**skill 与引擎不一致 = 下一个项目必然重踩。**
   同时检查**能力表与 `clover-doc` 的 `api-cheatsheet` 是否一致**（同一件事两处说法不同 = 隐患）。

注释里要写全这五段（缺一段下一个人就得重查），**直接写在受影响的类型 / 方法注释里**：

```csharp
/// <summary>
/// ⛔ <一句话说清缺陷：谁在什么条件下不工作>（★ 影响范围）
/// </summary>
/// <para><b>最小复现</b>：<可直接照抄的代码 + 修复前的实际输出 —— 不带这个就证明不了真是 bug></para>
/// <para><b>修复后自证</b>：<修复后通过 + 旧行为不变（带对照组）></para>
/// <para><b>已知边界 / 精度限制</b>：<防下一个人当万能药用></para>
/// <para><b>用法 + 首个消费方</b>：<怎么调；哪个项目哪一行在用 + 仍然存在的前提（业务自己还要接的线）></para>
```

> ⚠️ **不再用编号体系**：引擎仓库的集中台账已删除 ⇒ 编号没有登记处、查不到。
> 要交代"是同一处修复"，写**文件 + 方法名**；⛔ 不要再往注释 / 文档里写 `E-nn` 这类编号。

**同时**在 `docs/步骤文档.md` 或交付说明里写一行「本轮也修了引擎 N 处（`<文件>`:`<方法>` 列表）」。

**改了什么要写进引擎仓库的 `结构规则.md` / 索引（与本次改动相关的段落）**，⛔ 不要只在交付说明里说。

## 6. 端到端复跑：引擎改了，业务必须重验

引擎修复**只证明引擎对了**，业务链路要重跑：

1. 引擎：`go build` + `go vet` + 复现用例；
2. 业务服务端：`go build` + 起服 + 读日志（"XX 已接线"/"地图已构建"/mapdata 数字）；
3. 客户端：`recompile_status` 干净 → `editor_play` → 读运行日志**零异常** → 运行时自证 → 截图；
4. 跨进程行为（视野进出/推送/断线恢复）用**既有 PlayMode 端到端用例**跑一遍（explicit 断言 + 日志双保险）。

## 7. 什么情况**不该**改引擎

- 业务用通用 API 就能实现（**C 桶**：UI、数值、3D 表现、建图管线、匹配…）；
- 引擎只是"没配好/没接线"（缺配置、缺 `Wire*` 调用、缺 `CloverRes.Init` 这类业务初始化）；
- 私有诉求：为单个 demo 加业务专用字段/消息号 —— 那属于业务层。

> 判断口诀仍是 `patterns/game-demo.md` §0.2 的四桶：**A 已实现 / B 留了口 / C 业务自己写 / D 必须改引擎**。
> **只有 D 桶改引擎**；但 D 桶一旦确认，**就直接改**，不要再问。
