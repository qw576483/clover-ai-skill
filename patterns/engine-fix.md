# 引擎问题登记（**默认不改引擎**）

> **默认动作：⛔ 不改 skill、⛔ 不改引擎源码。** 发现引擎缺口 / 引擎 bug / skill 写错或说不清 ⇒ **写进 `<项目根>/引擎问题.md`，然后用绕法把活做完**（⛔ 不许停在这儿、⛔ 不许改源码绕过）。
> **唯一例外**：用户**本轮明说**"可以改引擎 / 顺手修引擎" ⇒ 才走本文档最后一节（改引擎 SOP）。

---

## 1. 为什么要写这份文件（而不是当场改）

- **引擎改动影响所有项目**：改一处 `Runtime/**` / `pkg/**`，所有在做的项目都被动跟着变；而当场改的人只对自己的 demo 负责。
- **改 skill 会让"基线"变成没人知道的东西**：主 agent 后续所有判断都建立在一个**没人知情的 skill**上。
- **绕过 ≠ 交付降级**：绝大多数引擎缺口在业务层都能绕（四桶里的 **C 桶**：UI、数值、3D 表现、建图管线、匹配…）。绕不过的 ⇒ 按"允许的差异"登记（`策划/验收表.md`），交付说明首行写明。

## 2. 文件格式（固定三段，一行一条）

落点：**`<项目根>/引擎问题.md`**（项目根，⛔ 不放进 `docs/`、⛔ 不放进 skill）。

```markdown
# 引擎问题（本项目遇到的）

> 由执行者随手记、主 agent 汇总去重。**不影响本轮交付**：能绕就绕，绕不过的登记进 `策划/验收表.md`。

## 引擎缺口
（"这类需求引擎本该有、但确实没有"——例如某个通用设施 / 配置项 / API）

| 现象 | 最小复现 | 影响 | 我们的绕法 | 建议 |
|---|---|---|---|---|
| `<一句话>` | `<能照抄的几行 / 命令>` | `<卡住什么、代价>` | `<业务层怎么绕的；绕不过 ⇒ 指向验收表那一行>` | `<建议引擎补什么>` |

## 引擎 bug
（"按文档 / 按签名用，结果不对"——行为与契约不符，或崩溃 / 静默失效）

| 现象 | 最小复现 | 影响 | 我们的绕法 | 建议 |
|---|---|---|---|---|
| `<现象 + 实际 vs 期望>` | `<复现步骤 + 实际输出>` | `<影响面>` | `<绕法>` | `<建议修复点：文件 + 方法名>` |

## skill 问题
（skill 写错 / 自相矛盾 / 说不清 / 缺条目 / 判断不出来该怎么做）

| 位置（文件 / 条款） | 问题 | 当时的场景 | 建议 |
|---|---|---|---|
| `<如 patterns/xxx.md §N>` | `<哪句错了 / 缺什么>` | `<做了什么时撞上>` | `<怎么改>` |
```

三条硬规则：
1. **一行一条，宁多勿少** —— 写不出最小复现的也照写，`复现` 列写"未复现"。**⛔ 不许因为"没复现"就不记**。
2. **发现即写**（执行者随手记，不必等回报）—— 丢掉的信息等于没发现。
3. **不许写成"抱怨稿"**：每行必须有「影响」与「绕法」，否则主 agent 无法裁决。

## 3. 谁写 / 谁汇总

| 角色 | 动作 |
|---|---|
| 执行者（team 成员） | 撞上就**追加一行**（⛔ 不改 skill / 不改引擎源码），继续干 |
| 主 agent | 交付前**去重 + 排序**（引擎 bug > 引擎缺口 > skill 问题），并在交付说明里写一行「本轮登记引擎问题 N 条（`引擎问题.md`）」 |
| 用户 | 决定哪些进引擎 / 进 skill |

**去重口径**：同一现象写多条 ⇒ 合并成一条，保留最小那条复现。

---

## 4. 唯一例外：用户**本轮明说**可以改引擎

> 此时标准换成下面的 SOP；**改完仍要在 `引擎问题.md` 记一行**指向那次修复（文件 + 方法名）。

### 4.1 三条铁律

| # | 铁律 |
|---|---|
| 1 | **先证明是引擎的 bug**：读源码 + 一个**最小复现用例**（跑起来就是失败 / 死锁 / 超时），再动手。**不许**"看着像 bug 就改" |
| 2 | **最小修复**：只改必需的行，不顺手重构、不动无关文件、不改公开签名（除非用户同意） |
| 3 | **修完必须自证**：引擎全量 `go build` + `go vet` + **跑复现用例**（修复前失败 → 修复后通过）+ 业务侧端到端复跑 |

### 4.2 定位：从"现象"走到"那一行"

| 现象 | 怎么定位 |
|---|---|
| 客户端收不到某类事件 | 从**消费端**回溯：客户端 `Runtime/**/*.cs` 的解析入口 → 消息号 → 服务端推送点（外层 key 是否与客户端解析格式一致） |
| 服务端逻辑"跑了但没效果" | 找到产出点 → `grep` 它的**订阅者**；**没有订阅者 = 事件进黑洞** |
| 死锁 / 卡住 / 超时 | 看**锁的作用域与回调时机**：持锁期间是否调用了会**同步回调**你的函数 |
| 偶发 / 时序 | 高频日志先看真实顺序（首次全量 + 之后每 N 次），不要猜 |

**判定标准**：能一句话说清「谁调用谁、在哪一行断掉」。说不清 → 继续查，别改。

### 4.3 三种典型修法

| 类型 | 症状 | 修法 |
|---|---|---|
| **事件无消费者** | 产出方算好了，客户端永远收不到 | 补下发：按**客户端真实解析格式**推送（消息号 + 外层 key 严格对齐） |
| **可靠性选错** | 不可重建状态（进 / 出视野）丢了客户端永远不知道 | 语义分级：不可重建状态走 `Reliable`；可重建高频增量才 `BestEffort` |
| **锁顺序 / 自锁** | 必然死锁 | 明确锁边界：**回调期间不持锁**；把"窗口锁"与"数据锁"拆开 |

### 4.4 日志 + 回归用例

```go
// 引擎侧高频失败日志范式
var failCount atomic.Uint64
func viewPushFailf(format string, args ...any) {
    n := failCount.Add(1)
    if n == 1 || n%1000 == 0 {
        logger.Warnf(format+" (累计 %d 次)", append(args, n)...)
    }
}
```

> **新功能不写单测**，但**为真实缺陷补复现用例属于排查手段，且必须补**：用例必须**先失败**（修复前），再在修复后**通过**；用**真实链路**而不是 mock；带**超时**（`go test -timeout 90s`）；文件 `*_test.go`，注释写清「复现什么缺陷 / 修复前现象 / 修复后断言」。

```bash
cd <engine>; go build ./... && go vet ./...
go test ./internal/domain/<模块>/ -run <你的用例> -v -timeout 90s
```

### 4.5 记录：写进**引擎源码注释 + 回归用例**（不另建台账）

注释里写全这五段，**直接写在受影响的类型 / 方法注释里**：

```csharp
/// <summary>
/// ⛔ <一句话说清缺陷：谁在什么条件下不工作>（★ 影响范围）
/// </summary>
/// <para><b>最小复现</b>：<可直接照抄的代码 + 修复前的实际输出></para>
/// <para><b>修复后自证</b>：<修复后通过 + 旧行为不变（带对照组）></para>
/// <para><b>已知边界 / 精度限制</b>：<防下一个人当万能药用></para>
/// <para><b>用法 + 首个消费方</b>：<怎么调；哪个项目哪一行在用 + 业务还要接的线></para>
```

**同时**改这三处，一个都不能漏：① `Runtime/**` 源码注释；② 引擎仓库内 `clover-client-unity-engine-index.md` / `结构规则.md` 的相关段落；③ **站点文档 `clover-doc/`**（对应模块那篇的 API 表 + 常见问题、`client/reference/api-cheatsheet.md`、属于"坑 / 约束"的进 `constraints.md`）。**文档与代码打架 = 下一个人照着文档写出错的东西。**

### 4.6 端到端复跑（引擎改了，业务必须重验）

① 引擎：`go build` + `go vet` + 复现用例；② 业务服务端：`go build` + 起服 + 读日志；③ 客户端：`recompile_status` 干净 → `editor_play` → 日志零异常 → 运行时自证 → 截图；④ 跨进程行为（视野进出 / 推送 / 断线恢复）用既有 PlayMode 端到端用例跑一遍。

### 4.7 什么情况**不该**改引擎

业务用通用 API 就能实现（C 桶）／引擎只是"没配好 / 没接线"（缺配置、缺 `Wire*`、缺 `CloverRes.Init`）／为单个 demo 加专用字段或消息号（属业务层）。

> 判断口诀 = 四桶：**A 已实现 / B 留了口 / C 业务自己写 / D 必须改引擎**。**只有 D 桶改引擎**；没拿到用户"可以改"的许可 ⇒ D 桶也**只登记、先绕过**。
