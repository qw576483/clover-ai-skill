# 为什么上一个项目做了那么久（17 个时间黑洞 + 3 条静默失败）

> 记录方式：**现象 → 正确做法 → 预防**。这些都是同一个项目里逐条发生过的。**"删库重建"时照着走，能把返工砍掉大半。**

## T1. 没先读引擎就写业务：漏了 `CloverRes.Init`，模型从头到尾没加载成功（★ 最贵）

- **现象**：客户端只显示胶囊体；"进去看不到角色"；`EnsureView` 抛 `NullReferenceException` 打断进图。
- **正确做法**：以为 `Game.Launch` 会把所有模块都挂上 —— 表现域确实自动挂，**但资源域（`Game.Res`）必须业务显式 `CloverRes.Init(root)`**。动手前先产出「模块挂载矩阵」：谁自动挂、谁必须业务挂（`Res` / `Input` / `Net` / `Data`），并写成启动顺序。
- **预防**：`reference/engine-mental-model.md` §1 直接照抄启动顺序；第一件事就是"把资源加载起来并打日志证明"。

## T2. 把"骨架能跑"当成果交付 → 被骂四轮"半成品"

- **现象**：链路通了就交付（能登录、能进图、位置能同步），但**没有操作、没有相机、没有动画、UI 是 OnGUI 调试字**；而且**一打开就直接站在游戏场景里** —— 没有启动画面、没有主菜单、没有创角。
- **正确做法**：**三段一次交付** —— ① 启动/菜单/创角链路 ② 首场景全部内容（场景/操作/相机/动画/UI/战斗/音效/复活）③ 游戏内流程（暂停/结算/回主菜单）；再按 `patterns/game-demo.md` §0.0c 的**原版系统清单**逐项做完。
- **预防**：`reference/game-delivery.md` §2 的 16 条铁律；开工就把系统清单贴在计划里逐项打勾，缺项不许交付；菜单链路照 `patterns/client/app-flow.md` 做。

## T3. 做一项汇报一次 → 用户暴怒

**正确做法**：只在 ① 被阻塞必须问用户 ② 全部做完 时说话；中间不播报进度（`reference/game-delivery.md` §2 第 9 条）。

## T4. 没有本地碰撞就做第三人称操作 → "被拽回来"的六环链条

- **现象**：往前走就被拽回原点；按 WASD 看着不动。
- **根因链**：客户端**完全没有碰撞**（连角色胶囊的 collider 都删了）→ 能穿墙/出图 → 服务端按地图拒绝 → 本地预测与服务端越差越大 → 最后被硬贴回。
- **正确做法（缺一不可）**：① **同一份地图数据**给客户端（引擎烘焙器一次写 `Assets/MapData/` 与 `Assets/Resources/MapData/`）；② 客户端**本地碰撞解算**：半径 8 向采样 + **分轴滑墙** + **扫掠细分（每段 ≤0.25m，防穿墙）**；③ 移动上行带**输入序号**，服务端拒绝时**回校正（带 ack）**，客户端「置权威值 + 丢弃已确认 + **回放未确认**」；④ **未进图/断线必须停发**（否则网关按 `unauthenticated` 拒绝并刷屏）。
- **预防**：本地碰撞 + 预测/校正/回放三件齐全（`reference/engine-mental-model.md` §3 / §5）。

## T5. 相机凭直觉做 → "被遮挡时不会避障"

- **现象**：镜头穿墙、被墙挡住却愣着、拉近后角色糊满屏。
- **根因**：把 `MinDistance` 当**硬下限** ⇒ 被挡时机位仍留在墙里；只探一条射线 ⇒ 墙沿露缝。
- **正确做法**：多高度探针取最小 + **被挡允许拉到 0.2m** + `CheckSphere` 重叠兜底 + 收缩快/恢复慢 + 贴脸隐藏角色 + 机位不钻地。（**动手前先搜标准做法**，别凭直觉。）
- **预防**：相机自写（`LateUpdate` 跟随 + `SphereCast` 防穿墙 + 收缩快恢复慢）—— `reference/engine-mental-model.md` §5 第 3 条。

## T6. 写死了"上帝视角"还不自知

**现象**：相机 `position = 角色 + (0,18,-14)`、`Euler(55,0,0)` ⇒ 用户："我进去是上帝视角，WASD 移动不了"。
**正确做法**：有角色就**必须**第三人称（或第一人称）：pitch/FOV/距离/灵敏度一开始就定，场景初始机位也按第三人称摆（参数写进《参考规格》）。

## T7. 重复登录 / 双实例 → 两个客户端同账号互相拽回

**现象**：日志**每条出现两次**；服务端 3260+ 条未鉴权拒绝；位置来回跳。
**根因**：① 场景里可能有**第二个 Bootstrap**（重复挂载）；② 后加的重连逻辑**把首次登录也触发了一遍**（重复登录 ⇒ 旧连接绑定被顶掉却仍在发消息）。
**正确做法**：`Awake` **单实例守卫**（多于 1 个自毁重复实例）；`LoginFlowAsync` 加**重入保护**；`Net.OnConnected` 只在"曾登录且本连接未绑定"时重登；**服务端还应有"同账号顶号"踢旧连接**。

## T8. 改了场景几何却没重导地图

**现象**：客户端看得见墙、服务端不挡（或反过来）。**正确做法**：**几何变更 = 必须重新烘焙**；引擎烘焙器一次写服务端与客户端两份；把这条写进项目 `constraints.md`（引擎地图烘焙器见 `reference/engine-mental-model.md` §4 的「地图 / 场景」行）。

## T9. 靠"看着像"验收 → 用户看到的和 AI 以为的完全不同

**现象**：AI 说"已经好了"，用户说"按 WASD 不动"。**正确做法**：**运行时自证**（`eval_file` 打印对象状态）+ **探针消息**（服务端权威答复）+ **截图**（含 HUD，PNG + 颜色多样性校验）+ **既有回归测试**；交付说明只能引用这些证据（`experience/verify-recipes.md`）。

## T10. 引擎高频失败日志不降频 → 刷屏

**现象**：一次断线刷 **3262 条** `unauthenticated`；另一处刷 **747 条**回包失败。**正确做法**：高频路径"首次 + 每 N 次"，精确次数交给 metrics；**改引擎要留痕**（根因写进代码注释 + 回归用例；业务项目 `constraints.md` 里写清"依赖了哪一处引擎修复"的 `文件:方法` + 回归方式）。见 `patterns/engine-fix.md`。

## T11. 低级几何错误（半格偏移 / 单位差异）靠探针才发现

**现象**：模型被放到"格角点"而非"格中心" ⇒ 整图偏移半格 ⇒ 探针在建筑外沿判"可走"；第三方 FBX 单位不一致 ⇒ 100 倍大或半埋。**正确做法**：**一律量测**（`Renderer.bounds` 反算缩放 + 按包围盒贴地 + 传格中心）；写完立刻用"点探针"验证几个关键点（量测优先见 `reference/engine-mental-model.md` §6）。

## T12. 没分层 → Bootstrap 上帝类

**现象**：一个文件里同时有登录流程、实体视图创建/销毁、模型加载与归一化、动画装配、HUD 刷新、热键/探针、相机装配 —— 改一处要动同一文件，一次网络异常引发全功能瘫痪。**正确做法**：`Def / Core / Module(每系统一个) / UI / App` 五层，依赖单向，模块只暴露一个门面接口，**App ≤ 200 行**（`reference/architecture.md`，含 **7 条**反耦合自检 grep）。

## T13. 工具用错：前台等 batch、被"项目已在编辑器中打开"卡住

**现象**：`unity run ... -executeMethod` 长时间前台等待；工程被用户开着时报错退出；console 输出被压成一行难以解析。**正确做法**：**驱动正在运行的编辑器**（`unity status` → `eval_file` / `editor_play` / `capture_game_view` / `recompile_status`）；长任务后台起 + 轮询；console 先落盘再用正则取 `"message"`（`reference/unity-cli.md` §8.1）。

## 如果重来一次：推荐顺序（照着走能省 80% 返工）

```
0. 读 skill → 读 experience/ → 读 reference/engine-mental-model.md（挂载矩阵 + 启动顺序）
1. 环境自检（服务端依赖 + Unity 6 + CLI）→ 建工程 → 登记 Hub 并置顶（让用户看得到）
2. 素材：按四级链找"目标游戏/同类游戏"的成套素材（能 clone/直链就自己下，不设许可门槛，记一行来源）
3. 服务端：消息号契约先冻结 → 起服 → 探针消息先可用
4. 地图管线：场景几何 → 引擎烘焙（一次写两份同源字节）→ 服务端 mapdata.Load + ApplyTo 日志确认 → 客户端 Game.Map 本地碰撞
5. 移动三件套：本地碰撞 + 预测/校正/回放 + 停发闸门（一次全上）
6. 相机：第三人称 + 遮挡避障（搬 core-code）
7. 动画：Editor 生成 AnimatorController → 运行时接 → 状态切换
8. HUD：真 uGUI 面板（预制体 + Game.UI.Open<T>）
9. 战斗闭环 + 音效（首场景必须包含）
10. 自证 + 截图 + 回归测试 → 参考游戏对照自审（不像就改）→ 一次性完整交付说明（含对照表逐项打勾）
```

## T14. 只"跑通"就交付，从没和参考游戏比过 → 用户一句"不像"全面返工（★ 最贵之一）

- **现象**：功能全在、日志全绿、自证数字也对，但用户看一眼就说"这不像 XX" —— 菜单层级不对、HUD 位置不对、手感不对、配色不对。
- **根因**：把"功能验收"当成了"交付验收"。**交付的唯一标准是"像不像参考游戏"**；而且审查时只看了数字 / 日志，**没看画面**。
- **正确做法**：① 动手前**必须有参考游戏名**（用户没给就**问用户要** —— 自己挑品类 = 必然返工）；② 准备 A 的参考截图 + 自己的**同角度**截图一一配对；③ 逐项对照，只允许写 `一致` / `不一致（差在哪）`；④ **只要有一项不一致 ⇒ 该版本不可交付**，改 → 重截 → 再对照，**循环到全部一致**。
- **预防**：`SKILL.md` 铁律 16；`patterns/game-demo.md` §0.0 第 0 / 4 步；`reference/design-review.md` §3.6。

## T15. 把 `go vet` / `go test` 当"秒级判据"跑 → 前台等到超时，一条判据都没拿到

- **现象**：交付前跑「四连」，`go build ./...` 秒回，`go vet ./...` / `go test ./...` 却**几十秒不返回**；换 `-vet=off`、换 `-c`、换缓存目录都没用；前台超时把它杀掉 ⇒ 报告里只能写"没跑成"，或者更糟 —— 把"被杀"当成"通过"。
- **实测（本机）**：**与缓存位置无关**（默认 `GOCACHE` 与工程内隔离缓存都复现）、**与包大小无关**（叶子包也一样）；**快的是** `go version` / `go build <pkg>` / `go list <pkg>`（亚秒级），`go build -o <exe> .` 也能跑完并产出二进制；**慢到不可用**的是 `go vet <pkg>` 与 `go test <pkg>`（含 `-vet=off`、含 `-c` 只构建不跑）—— **35 s 超时仍不返回（退出码 124）**。⇒ 这是**宿主 / 杀软层面的 I/O 等待**，不是"缓存没热"。
- **正确做法**：① **Go 判据交给后台长任务收**（后台起、输出重定向到文件、跑完再读）；**前台超时不算结论**，⛔ 也不要在超时后反复重试同一条命令。② 只要**产物真的重建了**（`-o` 产物 mtime **晚于**源文件），"go build 通过"这条就算拿到。③ **拿不到 `go vet` 就如实写"未取到"**，⛔ 不许写成"通过"。④ ⛔ **别把 `GOPATH` 指到空目录**去排除缓存因素 —— 那会强制重下全部依赖（实测 `go vet` 挂 29 分钟未完）。
- **预防**：交付清单里把 Go 判据标成**后台长任务**（与 `editor_play` 同类），而不是"随手一条命令、看一眼就完"。

## T16. "某个状态只存在 N 秒"时，先算**获取一次要多久**

- **现象**：要重采"启动画面 + 底部署名"那张图。`editor_play` 之后连续两次 `eval_file` 都落在 `scene=Main`；改试 `LoadScene("Boot")` + `Time.timeScale = 0` 想按住画面，结果拍到的是**登录页**，而且把同名的三张有效取证图覆盖掉了。
- **根因**：① 启动画面的停留是引擎自带 `Timer.After(...)`，**不吃 `Time.timeScale`**，冻结按不住它；② 真正跑不赢的是**进程往返**：窗口 2 s，而 `unity command eval_file` 起进程 + IPC 就要 1.5–2 s。
- **正确做法**：改用 `run_script` 的 **async 入口** —— 同一个进程里 `LoadScene("Boot")` 之后用**真实时间** `await Task.Yield()` 等 0.6 s 再截图，稳稳落在窗口内：
  ```bash
  unity command run_script --file <root>/.ai-tmp/drivers/xxx-boot.cs \
        --entry XxxBoot.Capture --timeout_ms 30000 --project-path <root>/client
  ```
- **预防**：凡"某个状态只存在 N 秒"的取证，先算**获取一次要多久**；获取耗时 ≥ 窗口 ⇒ ⛔ 别用逐次起进程的命令，改用一次跑完的长任务（`run_script` / 后台 loop）→ `reference/visual-loop.md` §8.2。

## T17. "改一个显示参数 → 立刻截图" = 整条序列**逐张错位一格**，而自检完全看不出来

- **现象**：12 张帧每张都比文件名所写的配置**滞后一格**（"设完立刻拍"拍到的是上一态"四层全 0"，而下一张"不设只拍"才是真正的正常态）⇒ 据此算出的读数**已被污染**，却一路当结论用了半天。
- **根因**：把「改参数」与「截图」放在**同一次 eval** 里 —— `CaptureGameView` 取的是**上一帧**已渲染好的后备缓冲，**不会为你重绘**。
- **正确做法**：**改一步、拍一步**（两次 eval）。术后自检：两张**没有任何状态变化**的连续帧如果长得完全不同，那只可能是截图滞后 —— **一条不需要知道机制就能判的判据**。
- **预防**：任何"改参数 → 截图"的实验都写成 `apply / capture` 两相；报告里贴一条「同状态连续两帧的差」当滞后自检（同一件事见 `reference/visual-loop.md` 第八节）。

## 静默失败三条（**编译不报错 / 日志不报警**，只有运行时读数或画面才现形）

> 与上面 17 条的区别：那 17 条至少**看得到**症状（报错、卡住、被用户骂），这三条**一条日志都不给你**
> ——「组件是 null」「画面空白」「内存暴涨」三种表现，**编译期全是绿的**。
> ⇒ 只能靠**运行时判据**抓（节点树读数 / 计数 / 唯一色数），⛔ 不能拿"编译过了 + 我在代码里写了"当证据。
> 判据怎么采见 `scaffold/probe-harness.md`。

### S1. 预制体的 `m_Script` 指向错 `fileID`（`fileID: 0`）⇒ 组件运行时为 null

- **症状**：面板 / 组件**运行时为 null**，`GetComponent<T>()` 拿不到；**编译期零报错**、Play 时也不抛异常，只是"什么都没发生"（最容易被误判成"逻辑没跑到"）。
- **根因**：**一个 `.cs` 里放了多个 `MonoBehaviour`** —— Unity 只把脚本引用解析到**与文件名同名的那个类**，其余的挂不上；序列化进预制体就落成 `m_Script: {fileID: 0}`。
- **判据**：① 机械（离线）：**一个 `.cs` 一个 `MonoBehaviour`**（逐文件数 `: MonoBehaviour`，>1 即违规，见全局 `SKILL.md` 的「写码清单」第 8 条「工程卫生」）；② 机械（离线）：对预制体 grep `m_Script: \{fileID: 0\}`，命中即违规；③ 运行时：进场后逐个打印关键组件的 `Game.UI.Get<T>()` / `GetComponent<T>()`，**拿到 null 就 `Error`** ——"代码里写了"不算，**活节点树上的读数**才算。

### S2. `AudioListener` 挂在会被切换的场景相机上 ⇒ 每次切场景刷屏、内存暴涨

- **症状**：每次切场景日志被刷屏（同一条告警每分钟成百上千条），日志文件十几分钟涨到 **74 MB**，内存跟着涨；画面本身正常，所以极容易只当成"日志有点多"。
- **根因**：`AudioListener` 随**场景相机**被销毁 / 重建 ⇒ 场景切换的瞬间全场 listener 数变成 0（或短暂出现 ≥2），引擎每帧告警。
- **判据**：① 机械：`AudioListener` **必须挂在常驻物体**（`DontDestroyOnLoad` 的根物体 / Bootstrap）上，⛔ 不许挂场景相机；② 运行时：跨场景采样 **listener 数恒为 1**（0 或 ≥2 都打 `Error`）；③ 日志：**同一条告警的单位时间出现次数**要能被断言（"刷屏" = 判据红），⛔ 不许靠"我看了眼日志觉得还行"。

### S3. 面板栈 `CloseAll()` 之后 `Transition(同一个状态)` 是 **no-op** ⇒ 空白屏且**零日志**

- **症状**：**画面空白 + 一条日志都没有**。"清面板 → 切回（当前所在的那个）状态"之后，状态机不动、面板也不重建 ⇒ 看起来像界面挂了，却**无从排查**（没有报错、没有异常、没有日志线索）。
- **根因**：① 状态机对"切到**当前所在状态**"是 **no-op**；② UI 的 `Open<T>` 在"注册表里**已有该类型**"时**直接走 OnOpen 返回**，不新建、不报错。
- **判据**：凡是"**先清面板、再靠状态切换把界面带回来**"的地方，**必须先判当前状态**：同状态 ⇒ **自己显式 `Open<该面板>()` 并打一行日志**（"界面已重建"）。机械判据 = 这条路径上**必有一行重建日志**，**没有这行标记就判红**；"整个路径零日志"本身就是最强症状，⛔ 不许当"没报错 = 正常"。
