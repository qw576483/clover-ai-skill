# 逐帧现象的取证通道 + 判据事故案例

> **什么时候读这一页**：用户报的现象是**逐帧**尺度的 —— "抖 / 飘 / 抽搐 / 滑步 / 一顿一顿 / 攻击被打断 / 贴图闪回 / 朝向乱翻 / 单位互相盖"。这类现象 `eval_file` 的**调用粒度**（一条链里 5~6 s 一次 = **0.2 Hz**）**判不了**，必须开逐帧通道。
> `SKILL.md` §4 第 11 条与 §5 第 3 条是**摘要**，这一页是**全文**：做法 / 口径 / 事故。

---

## 一、通道怎么搭（照抄即可）

1. **钩子**：在 `eval_file` 的驱动里注册 `UnityEditor.EditorApplication.update += Tick`（`UnityEditor` 在 `eval_file` 里**可直连**），每帧采一次、攒 `StringBuilder`、按阈值 `File.AppendAllText` 落 TSV；退出时 `update -= Tick`（⛔ 不留残留钩子）。
2. **终止必须是显式可失败条件**（三选一）：出现 stop 文件 / 帧数超预算 / 时长超预算。⛔ 不要靠"链跑完自然停"。
3. **每条 TSV 行都要带 `frame` + 真实 `dt`** —— 但**分母别用 `dt`**（见 §二.1）。
4. **同时写一条 `clock` 行**（每帧一行、**无战斗也写**）⇒ 钩子活没活可以立刻自证。
5. **存活判据 = 两条一起看**：① 采样器日志里有 `hook registered`；② 行数在增长。⛔ **不能只看"注册后 N 秒磁盘上的行数"** —— 采样器把数据攒在 256 KB 缓冲里时，8 s 内磁盘上只有表头 1 行，会把**活着的**钩子判死 ⇒ flush 阈值要小（16 KB 量级）。
6. **反射口径**：`eval_file` 与 app **不在同一 `AssemblyLoadContext`** ⇒ 只能按 `Type.Name` 字符串反射、`GetField(name, NonPublic|Instance)`；基本类型与委托可用，但 `System.Action` / `Func` 是泛型 ⇒ 必须写 `System.Action<string>`。`FindObjectsByType<T>()` **⛔ 不带 `FindObjectsSortMode`**（本版本 obsolete-as-error）。
7. **采集窗口要覆盖被判现象**：用户说"打人**时**抽搐" ⇒ 必须采到攻击段（判据 = 逐帧表里 `anim==2` 的行数 > 0，**别拍脑袋定秒数**），采到后再多采几轮。⚠️ 还要加一条**场上单位数**条件：只采到"攻击段"不够 —— 若那一刻场上只有 1 个单位，"苍蝇海"根本没出现 ⇒ 判据应是"`units >= 12` 峰值达标 **且** 攻击段出现"。

## 二、三个真实事故（每个都改了判据或流程）

### 1. ⛔ 分母口径：别用 `Time.deltaTime` 当"过了多少时间"

`Time.deltaTime` 被 Unity 夹在 `Time.maximumDeltaTime`（默认 **1/3 s**），而渲染时钟走的是**不被夹取**的 `Time.realtimeSinceStartup` ⇒ 一次卡顿里位移是真实一段时间的位移、分母只记了 333 ms ⇒ **算出来的瞬时速度凭空放大 2 倍以上**。
**判据**：采样行里出现 `dt=0.3333`（正好等于夹取值）就是它。**正确做法**：分母用**时钟自己的推进量** `ΔrenderMs`（把 `clock` 表按 `frame` join 上来），它与位移同源。

### 2. ⛔ 进 Play 必须显式校验，否则症状会伪装成"钩子坏了"

`command editor_play` 会**返回空串**（编辑器刚做完 domain reload 时尤其常见）。按"空返回 != 失败"的规则它会被放过去，而编辑器其实**没进 Play**（探针读数 `playing=False frameCount=1 scene=Main`）。接着：钩子注册"成功"，但**编辑态里 `Time.frameCount` 不推进** ⇒ Tick 里的"帧没变就 return"让**一行都不写**（clock 表永远只有表头 1 行）⇒ 整条链报 **`HOOK DEAD`** ⇒ **把病因错误地归到钩子身上**。
**⇒ 发完 `editor_play` 必须探测 `Application.isPlaying`**（探针打 `playing / frameCount / scene / rootCount / editorUpdateHooks / samplerLogTail`），最多重试 5 次，5 次都不行才判红。

### 3. ⛔ 残留 tick 会和你抢同一张表

上一条链中止时钩子仍挂在 `EditorApplication.update` 上（判据：探针的 `editorUpdateHooks` **从 28 → 27** 才是我们那一个摘掉了）。残留 tick 与新注册的 tick **同时写同一张 TSV** ⇒ 重复行、判据全乱。
**⇒ 两步固定动作**：① **发车前**无条件写一次 stop 文件、等 8 s 让它自摘、**再删掉**；② **收工时**写的必须是钩子**真正监视的那个文件名**。⛔ 只写一个"另一个名字的 finish 文件"等于没收工 —— 钩子会一路采到编辑态去（`EditorApplication.update` 在编辑态依然有效），把 clock 表灌满"单位数 = 0 的编辑态帧"，直接污染 `t` 的分布统计。收工后要有一条**能失败**的核对：行数在读 stop 前后**必须不变**。

## 三、判据侧：`--corrupt` 负控必须"打中自己那条"

- 全量负控跑完是**必要条件不是充分条件**：`--corrupt clock` 原本只把第一个样本乘 1.4，而对应判据取的是 **7513 个样本的中位数** ⇒ 一个离群点根本不动中位数 ⇒ 判据**照样 PASS** ⇒ 这个负控等于没做（它当时"转红"只是因为基线本身就红，属于**假通过**）。**修法 = 让注入量作用在统计量本身上**（整体缩放 ⇒ 中位数随之变）。
- ⇒ **每条负控都要核对"红的确实是它自己那条"**，而不是"rc=1 就算过"。

## 四、判据修正的两个原则

- **假红**：写成"过去 3 帧内出现过同值就 +1" ⇒ 在一条 862 帧的**稳定**游程里**每帧都命中** ⇒ 12/12 个单位全红。**形状识别法**：**命中数 ≈ 总帧数 ⇒ 几乎一定是口径错**（不是缺陷）。改**游程口径**（"X→Y→X 且 Y 的连续长度 ≤ N"）后真值只剩 2 个单位 4 处。
- **永远不可能通过**：判据量到的是**素材自身**的性质（如"可见脚线极差 ≤0.06 格"量到的其实是原画腿部循环）⇒ **修代码永远不可能让它变绿**。改判**真正属于本工程的不变量**（如"`rect.min + pivot` 逐帧恒定"）。
- **剔除瞬态 ≠ 隐藏证据**：某段瞬态会顶高 p95 时，正确做法是**两条判据** —— 稳态（剔除"单位首次出现后 N 帧"）+ 另一条**单列判它**。⛔ 不许只删不判。

## 五、抖动**不在表现层**的时候：上游每 tick 位移必须有界

拿到逐帧表之后，**第一件事是判"抖动的源头在客户端还是服务端"**，别默认是表现层。

**取证链**（用 §一 的逐帧表就能把"哪一格"钉出来）：`units` 表里按 id 逐格算位移，找**离群格** —— 某一格位移是前后格的 **3~4 倍**且方向还反了 ⇒ 跟的是一个 **`server_ms`（服务端时间戳）**，所以"同一格内位移离群" = **服务端在一个 tick 里走了一大步**，不是客户端画歪了。

**根因**：服务端碰撞分离把两单位的**重叠量在一个 tick 内全部分完**；服务端 20 Hz tick 本身没问题，但客户端是 **10 Hz 快照 + 线性插值** ⇒ 两个快照点之间的直线在快照点处**速度不连续** ⇒ 那一格被原样播成"**一帧冲一大步**"。

> ⚠️ **别因为"和参考实现一致"就判无缺陷** —— 参考实现与本项目**逐字一致**（就是"一次分完、不限速"），因为它跑的是 **60 fps 本地模拟**，同一份分离被摊成了逐帧小步。⇒ **同一算法在不同 tick / 快照频率下表现不同**：「算法对」≠「在这套频率下表现对」。

**⛔ 先证否客户端方案，再动服务端**（这一步能省掉整片返工）：最顺手的想法是"让客户端插值更平滑"。**别直接改客户端** —— 先写一个**离线重放脚本**：把逐帧表里的**真实快照点**喂进去，同时重放"线性 vs 新方案"，跑同一套判据。若新方案在判据上更差 ⇒ **方案被自己的仿真证否**，客户端改动全部回滚，省掉整片返工。
> 可复用结论：**任何"穿过快照点"的插值都躲不开这段位移，只会把峰值摊得更高；要平滑就必须引入滞后** ⇒ 无滞后可选的场合，**唯一修法是让源头的逐 tick 位移有界**。

**修法**：给分离加「**逐 tick 位移上限**」= 该单位**自己走一步**的距离。物理上自洽：**被推速率不超过主动移动速率**。
⚠️ **额度必须"整个 tick 共享"**：一个 tick 跑多个 pass ⇒ 若按"每次分离调用各给一份"，同一只单位会被多个邻居各推一次、合计远超上限。改成**每 tick 一张 `used` map 在 pass 间共享**后，最坏值才落在界内。

**⚠️ 凡"参考实现没有的约束"，一律登记为「允许的差异」**：写进 `策划/验收表.md` 的「允许的差异」+ 差异登记表，四栏（是什么 / 为什么 / 出处 / 何时消除）俱全，`何时消除` 写 **⛔ 不消除（有意引入）**。⛔ 不登记 = 等于偷偷改参考行为。

**判据 + 负控**：多条单测锚住行为（单次调用 ≤ 一步 / 限速下 N tick 仍能分开 / 轻微重叠不回归 / 群体最坏位移 ≤ 界）；**负控 = 把额度函数临时 `return 0`**（关掉限速）⇒ 断言转红 ⇒ 证明判据有区分力。
⚠️ 改这类"旧约定"时，**既有断言可能正是在锚那条旧约定**（如某条断言"一次分离就分到底"，而"一次分完"正是要改掉的东西）⇒ 修法 = 加一个循环 `settleCollisions()` 来适配新时序，**判据意图不变**，⛔ **不是删断言**。

## 六、限速之后必然要问的第二句：**它有没有把"冲刺"换成"来回顶牛"**

"给位移加上限"是个**只做了半件事**的修法：一次性大位移被压住了，但**持续的小位移来回**要靠**反向次数判据**抓出来（实机上出现过"上限修绿了 A1/A1b、A2 反向反而变差"）。

**判"振幅还是事件"**：先算**总量**再算**速率** —— 若总反向次数与超标单位数**整体下降**、只是剩下那一坨集中在**很短的窗口**里被短行走窗放大成"频次变高" ⇒ **不是"变差"，是"一个堆叠团在解堆时抖了 6 次"**。这个区分决定了你是"回滚"还是"接着修"。

**用轨迹把几何钉出来**（⛔ 不要凭猜）：dump 那一段的 `frame / wx / wy / anim` —— 若 `wx` 恒定（一条竖直车道）、前排单位 `wy` 恒定不动而在交火 ⇒ 就是"**前排停下、后排压上**"的排队几何。

**⛔⛔ 最关键的一步：把所有单位冻结，只跑碰撞解算** —— 这是把"移动"和"分离"两个变量**隔离**的最小实验：单位全部不动、只调解算器，若**依然每 tick 来回振、跑满数百 tick 仍不停** ⇒ 振荡**与"走"无关**，是**解算器自身的性质**。
（两次白费的弯路记下来：① "走到贴住同伴就停" ⇒ 更糟；② "单纯把额度调更小" ⇒ **仍然振** —— **额度大小不影响**这个振荡，这是第一条诊断线索。）

**根因是一条初中数学**：设单位有 **n** 个贴住的同伴、沿某轴位置 x，它这一 tick 收到的分离位移 ≈ `Σ(overlap_i/2)`，而 `overlap_i = limit − |x − x_i|` ⇒ **∂(位移)/∂x = −n/2** ⇒ 离散松弛的**误差增益 = 1 − n/2** ⇒ **n ≥ 4 时 |增益| ≥ 1 ⇒ 不是收敛而是等幅/发散振荡。**

⇒ **修法：把累加量除以 n（取"平均"而不是"求和"）**，增益恒为 `1 − 1/2 = 0.5`、与 n 无关 ⇒ 恒收敛。而且 **n=1（最常见的轻微重叠）时是完整修正、一个 tick 解决**，**不为阻尼付代价**（试过"除以常数 2 当欠松弛"⇒ 把"轻微重叠一 tick 解决"那条判据弄红了）。

**还必须配套的两件事**（少一件都会翻车）：
1. **先累加、后落地**（纯累加阶段不改位置 → 统一落地）。逐对**立即**施加时，"被夹在两只同伴中间"的单位先被一侧推 `+d`、再被另一侧推 `−d`，两次位移**不抵消**（还被额度裁掉反向那份）⇒ 净位移永远偏向先施加的一侧；累加后反向自然抵消。
2. **额度按"累加向量的模长"取一次**，⛔ 不是"每一对推力各裁一次"。

**判据 + 负控（两个负控都要打中"新写的那个东西"）**：正控 = 一 tick ≤ 一步 / 群体最坏位移有界 / **只跑分离时反向 == 0**；负控 A = 额度函数 `return 0` ⇒ 转红（证明"上限"有区分力）；负控 B = 关掉"取平均" ⇒ 转红（证明"振荡"有区分力）。
⚠️ **起始瞬态要单列、但只跳起点**：深堆叠起步的前若干 tick 会有 1~2 次方向修正 ⇒ **只跳起点、不跳过程中的任何一帧**，且必须**明写**在判据注释里（⛔ 不要悄悄把窗口挪到不红为止）。

**登记**：这是**第二条**参考实现没有的约束（参考是"逐对立即施加 + 固定多轮"）⇒ 与上一条**分开登记**（上限 / 解算器形态），理由不同、出处不同，别合并成一行。
